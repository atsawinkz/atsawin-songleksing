# สรุปปัญหาและวิธีการแก้ไขในระหว่างการพัฒนาโปรเจกต์ (Project Implementation Issues)

ในกระบวนการพัฒนาระบบแชทบอทวินิจฉัยโรคข้าว (ทั้งในส่วนของ RT-DETR, การจัดการ Dataset, ระบบ RAG และ LINE Integration) ทางผู้วิจัยพบปัญหาทางเทคนิคระหว่างการดำเนินการ ซึ่งได้ทำการแก้ไขเพื่อให้ระบบทำงานได้อย่างสมบูรณ์ ดังนี้:

## 1. ปัญหาข้อจำกัดปริมาณการใช้งาน API (API Rate Limit & Quota Exceeded)
- **ลักษณะปัญหา**: ระหว่างการรันสคริปต์ประเมินผล RAGAS ด้วยคำถามทั้ง 80 ข้อ ระบบเกิดข้อผิดพลาด `ResourceExhausted: 429 Quota exceeded` จนโควตารายวันหมดและหยุดการทำงานลงกลางคัน (รันค้างอยู่ที่ประมาณ 33%)
- **สาเหตุ**: การใช้ API Key ของ Google Gemini ในรูปแบบบัญชีฟรี (Free Tier) จะถูกจำกัดโควตาการใช้งานที่เข้มงวด แม้จะมีการพยายามเปลี่ยนจากโมเดลรุ่น `Gemini 2.5 Flash` (20 ครั้ง/วัน) มาเป็นรุ่น `Gemini 3.1 Flash Lite` (500 ครั้ง/วัน) แล้ว แต่เนื่องจากกระบวนการตรวจข้อสอบของ RAGAS จะต้องยิง API วัดผลแบบ 4 มิติในทุกๆ คำถาม (รวมต้องใช้ API มากกว่า 320 ครั้ง) ทำให้โควตารายวันทะลุขีดจำกัดอย่างรวดเร็ว
- **วิธีการแก้ไข**: 
  1. **การหน่วงเวลาเพื่อหลบ Rate Limit**: ในส่วนของการตอบคำถาม (Generation) ได้เพิ่มคำสั่ง `try-except` เพื่อดักจับ Error 429 และสั่งหน่วงเวลา `time.sleep(15)` ก่อนพยายามยิงซ้ำ ซึ่งช่วยให้การสร้างคำตอบ 80 ข้อสำเร็จลุล่วงและสามารถบันทึกไว้ในไฟล์ `eval_results.json` ได้
  2. **แยกกระบวนการและสลับ LLM เป็นค่ายอื่น (Decoupled Evaluator)**: เพื่อแก้ปัญหาโควตารายวันหมด ผู้วิจัยได้ทำการแยกโค้ดส่วนกรรมการประเมินผลออกเป็นไฟล์ใหม่ (`evaluate_with_opencodezen.py`) โดยเปลี่ยนไปเรียกใช้โมเดลของค่ายอื่นที่ให้โควตาฟรีที่เสถียรกว่า เช่น **DeepSeek V4 Flash Free** (ผ่านแพลตฟอร์ม OpenCode Zen) ให้รับบทเป็นกรรมการตรวจ (Judge) แทนโมเดลของ Google ช่วยปลดล็อกข้อจำกัดด้านโควตา และทำให้โปรแกรมรันประเมินผลต่อไปจนจบได้อย่างราบรื่น

## 2. ปัญหาการเชื่อมต่อโมเดลของ RAGAS (Evaluator Model Mismatch)
- **ลักษณะปัญหา**: แม้ผู้ใช้งานจะกำหนดให้ใช้ Gemini สำหรับการตอบคำถาม แต่กระบวนการตรวจข้อสอบให้คะแนนของ RAGAS ใช้งานไม่ได้
- **สาเหตุ**: ค่าเริ่มต้นของไลบรารี RAGAS ถูกตั้งโปรแกรมมาให้เรียกใช้โมเดลของ OpenAI ในการเป็นกรรมการให้คะแนน ทำให้เกิดข้อผิดพลาดเพราะระบบไม่มี API Key ของฝั่ง OpenAI
- **วิธีการแก้ไข**: เพิ่มการตั้งค่าเชื่อมโยง `ChatGoogleGenerativeAI` เข้าไปในโมดูลของ RAGAS โดยตรง เพื่อบังคับให้ตัวประเมินผล (Evaluator) ใช้โมเดล Gemini ในการให้คะแนนแทน พร้อมกับระบุการจำกัดการประมวลผลพร้อมกัน (`max_workers=1`) เพื่อไม่ให้ยิง API เร็วเกินไป

## 3. ปัญหาความเข้ากันได้ของ Pinecone Vector Database
- **ลักษณะปัญหา**: โค้ดสร้างฐานข้อมูลแจ้งข้อผิดพลาดว่าไลบรารีไม่ถูกต้อง รวมถึงเกิดข้อผิดพลาดแจ้งเตือนขนาดมิติ (Dimension Mismatch) ระหว่างอัปโหลดข้อมูล
- **สาเหตุ**: 
  1. ไลบรารีทางการของ Pinecone มีการเปลี่ยนชื่อแพ็กเกจใหม่จาก `pinecone-client` เป็น `pinecone`
  2. โมเดล Embedding ฝั่ง Gemini (`models/gemini-embedding-001`) สร้างผลลัพธ์เวกเตอร์ที่ความยาว **3,072 มิติ** ซึ่งกว้างกว่าที่ออกแบบโครงสร้างฐานข้อมูลเริ่มต้นไว้ที่ 768 มิติ
- **วิธีการแก้ไข**: ถอนการติดตั้งไลบรารีตัวเก่าและอัปเดตไลบรารีของ Pinecone เป็นเวอร์ชันล่าสุด จากนั้นทำการลบตาราง (Index) เดิมทิ้ง และเขียนสคริปต์สร้างฐานข้อมูลใน Pinecone ใหม่ให้รองรับขนาดเวกเตอร์ที่ 3,072 มิติ

## 4. ปัญหาการแสดงผลภาษาไทยขัดข้อง (Windows Encoding Error)
- **ลักษณะปัญหา**: สคริปต์รันทำงานจนหยุดชะงักพร้อมแจ้งข้อผิดพลาด `UnicodeEncodeError: 'charmap' codec can't encode characters` 
- **สาเหตุ**: การประมวลผลผ่าน Command Prompt หรือ Terminal บนระบบปฏิบัติการ Windows มักมีปัญหาการแสดงผลและเข้ารหัสตัวอักษรภาษาไทย
- **วิธีการแก้ไข**: นำเข้าไลบรารี `sys` และ `io` เพิ่มเติม เพื่อเขียนโค้ดบังคับการเข้ารหัส (Encode) หน้าจอแสดงผล (Standard Output) ให้ใช้รูปแบบ `UTF-8` ทำให้สามารถปริ๊นท์ข้อมูลภาษาไทยออกมาระหว่างที่โปรแกรมกำลังทำงานได้ตามปกติ 
  *(อัปเดตเพิ่มเติม)* การครอบ `sys.stdout` ด้วย `TextIOWrapper` ทำให้เกิดปัญหา **Output Buffering** ทำให้การปริ๊นท์ข้อความสถานะ (เช่น Progress Bar) ไม่แสดงผลแบบ Real-time จึงต้องเพิ่มพารามิเตอร์ `line_buffering=True` เข้าไปด้วย (`sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', line_buffering=True)`)

## 5. ปัญหาการเตรียมชุดข้อมูลภาพและการตีกรอบ (Dataset Preparation & Labeling)
- **ลักษณะปัญหา**: กระบวนการสร้างและจัดเตรียมชุดข้อมูลรูปภาพ (Image Dataset) สำหรับใช้ฝึกสอนโมเดลตรวจจับวัตถุ เป็นขั้นตอนที่กินระยะเวลาและแรงงานสูงมากที่สุด (Time-consuming) ในโครงงาน
- **สาเหตุ**: การที่จะทำให้โมเดล Object Detection (เช่น โมเดลตระกูล YOLO หรือ RT-DETR) สามารถตรวจจับและแยกแยะประเภทโรคข้าวได้อย่างแม่นยำ จำเป็นต้องใช้ภาพถ่ายใบข้าวจำนวนหลายพันภาพ และต้องอาศัยความละเอียดถี่ถ้วนในการวาดกรอบ (Bounding Box) และแปะป้ายกำกับ (Labeling) ระบุตำแหน่งของแผลโรคบนภาพทีละใบให้ถูกต้องตามหลักวิชาการ
- **วิธีการแก้ไข/แนวทางรับมือ**: 
  1. การนำชุดข้อมูลภาพถ่ายโรคข้าวแบบสาธารณะ (Public Dataset) ที่ผ่านการรับรองจากผู้เชี่ยวชาญมาใช้งานเป็นฐานเริ่มต้น เพื่อลดระยะเวลาที่ต้องลงพื้นที่ถ่ายภาพและแปะป้ายใหม่ทั้งหมด
  2. เลือกใช้เครื่องมือและแพลตฟอร์มที่ช่วยอำนวยความสะดวกในการทำ Annotation (เช่น Roboflow, LabelImg, หรือ CVAT) ซึ่งมีฟีเจอร์ช่วยตีกรอบได้รวดเร็วขึ้น และจัดสรรเวลาของแผนงานโดยเผื่อเวลาสำหรับการคลีนข้อมูลรูปภาพ (Data Cleaning) ให้มากขึ้น

## 6. ปัญหาการบันทึกผลลัพธ์จาก RAGAS Evaluation (KeyError: 0)
- **ลักษณะปัญหา**: หลังจากรันกระบวนการประเมินผลครบทุกข้อจนจบ 100% โปรแกรมกลับเกิดข้อผิดพลาด `KeyError: 0` ในขั้นตอนสุดท้ายที่กำลังจะแปลงผลลัพธ์คะแนน (EvaluationResult) ออกมาเพื่อเขียนบันทึกลงไฟล์ JSON ส่งผลให้ข้อมูลผลการประเมินที่รันมาทั้งหมด (ซึ่งใช้เวลาหลายชั่วโมง) สูญหายและไม่ได้ถูกบันทึก
- **สาเหตุ**: การอัปเดตเวอร์ชันของไลบรารี Ragas ทำให้คลาส `EvaluationResult` ไม่รองรับการแปลงเป็น Dictionary ด้วยคำสั่ง `dict(s)` แบบตรงไปตรงมาอีกต่อไป เมื่อใช้คำสั่งดังกล่าว โปรแกรมจะพยายามเข้าถึงคีย์ที่เป็นตัวเลข (Index 0) ทำให้เกิด KeyError 
- **วิธีการแก้ไข**:
  1. **เปลี่ยนวิธีการเข้าถึงข้อมูล**: แก้ไขโค้ดจากการใช้ `dict(s)` เปลี่ยนมาใช้ฟังก์ชัน `s.to_pandas()` เพื่อแปลงผลลัพธ์ให้อยู่ในรูปแบบของ Pandas DataFrame ซึ่งมีความเสถียรและสามารถจัดการข้อมูลได้ง่ายกว่า
  2. **เพิ่มระบบบันทึกผลรายข้อ (Checkpoint)**: ใช้คำสั่ง `df.to_csv('eval_details.csv')` เพื่อให้ระบบเซฟผลคะแนนแบบแยกรายข้อลงไฟล์ CSV ไว้ก่อนทันทีที่ได้ DataFrame เพื่อป้องกันกรณีโปรแกรมแครชระหว่างการคำนวณค่าเฉลี่ย
  3. **คำนวณค่าเฉลี่ยเอง**: ดึงคอลัมน์ของแต่ละ Metric จาก DataFrame มาคำนวณด้วย `df[m].mean()` แล้วจึงเก็บเป็น Dictionary ของผลรวมเฉลี่ยเพื่อบันทึกลงไฟล์ JSON ต่อไป

## 7. ปัญหาข้อจำกัดของ Provider API ในเกณฑ์ Answer Relevancy (Invalid n value)
- **ลักษณะปัญหา**: ระหว่างที่ RAGAS กำลังตรวจข้อสอบในเกณฑ์ความตรงประเด็น (Answer Relevancy) โปรแกรมเกิดข้อผิดพลาด `BadRequestError: Error from provider (DeepSeek): Invalid n value (currently only n = 1 is supported)` ทำให้ได้ค่าคะแนนกลับมาเป็น `NaN`
- **สาเหตุ**: กลไกการทำงานของเกณฑ์ `answer_relevancy` ใน RAGAS จะทำการแต่งประโยคคำถามย้อนกลับ (Reverse Engineering) จากคำตอบจำนวน 3 แบบพร้อมๆ กัน โดยส่งพารามิเตอร์ `n=3` ไปยังโมเดล LLM แต่ผู้ให้บริการ API ฝั่ง DeepSeek (ผ่าน OpenCodeZen) จำกัดให้ส่งคำขอที่ `n=1` เท่านั้น
- **วิธีการแก้ไข**: เพิ่มคำสั่งตั้งค่าการทำงานก่อนรัน RAGAS โดยบังคับให้ลดจำนวนการสุ่มคำถามย้อนกลับเหลือเพียง 1 ชุด ด้วยคำสั่ง `answer_relevancy.strictness = 1` แม้จะทำให้คะแนนอาจแกว่งขึ้นเล็กน้อย (ไม่มีตัวหารเฉลี่ย) แต่สามารถหลีกเลี่ยงข้อผิดพลาดจากฝั่ง API และประเมินผลต่อจนจบได้อย่างรวดเร็วและราบรื่น

## 8. ปัญหาเซิร์ฟเวอร์ตอบสนองไม่ทันและการติดจำกัดโควตา (TimeoutError & Rate Limit)
- **ลักษณะปัญหา**: ระหว่างการรันประเมินผลด้วย RAGAS ผ่าน API ของ OpenCodeZen (DeepSeek V4) ไปได้ระยะหนึ่ง (ประมาณ 70%) โปรแกรมแสดงข้อผิดพลาด `TimeoutError()` เรียงติดกันหลายข้อ และบางข้อขึ้น `Error 503: Service is too busy` ส่งผลให้คะแนนในข้อเหล่านั้นหายไปและกลายเป็นช่องว่าง (`NaN`)
- **สาเหตุ**: เนื่องจากเป็นการรันข้อสอบรวดเดียว 70 ข้อ (รวมการประเมิน 4 เกณฑ์ ทำให้ต้องเรียก API ถึง 280 ครั้งในเวลาไล่เลี่ยกัน) ส่งผลให้โควตา API แบบฟรีรายวันถูกใช้จนหมด (Quota Exceeded) หรือระบบของฝั่งผู้ให้บริการมองว่าเป็นการส่งคำขอที่ถี่เกินไป จึงทำการตัดการเชื่อมต่อ (Throttling) ชั่วคราว
- **วิธีการแก้ไข**:
  1. **ข้ามข้อที่ Error เพื่อรักษาผลลัพธ์ส่วนใหญ่**: ปล่อยให้โปรแกรมรันต่อไปจนจบโดยอาศัยการตั้งค่า `raise_exceptions=False` ใน RAGAS เพื่อป้องกันโปรแกรมหยุดทำงาน (Crash) ทำให้สามารถรักษาคะแนนส่วนใหญ่ที่ตรวจผ่านแล้วเซฟลงไฟล์ `eval_details.csv` ได้สำเร็จ
  2. **สร้างสคริปต์ซ่อมแซมเฉพาะจุด (Patching Script)**: สร้างสคริปต์ `03_fix_evaluate_scores.py` เพื่อโหลดไฟล์ CSV กลับมาสแกนหาเฉพาะข้อที่มีคะแนนเป็น `NaN` จากนั้นใช้ API Key อันใหม่ (ผ่านการสมัครอีเมลใหม่) มารันประเมินซ้ำ **เฉพาะข้อที่พัง** แล้วนำคะแนนมาเสียบอุดรูรั่วในตารางเดิมให้เต็ม วิธีนี้ช่วยประหยัดเวลาและโควตา API ได้ดีกว่าการต้องเริ่มรันใหม่ตั้งแต่ข้อแรกทั้งหมด
