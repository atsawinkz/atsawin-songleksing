## 5.1 สรุปผลการดำเนินงาน

ผู้พัฒนาได้ดำเนินการพัฒนาระบบเชี่ยวชาญเพื่อการวินิจฉัยโรคพืชในข้าวและให้คำแนะนำด้วยปัญญาประดิษฐ์ผ่านแอปพลิเคชันไลน์ ได้ครบถ้วนตามขอบเขตและวัตถุประสงค์ที่ได้ระบุไว้ในบทที่ 1 โดยระบบสามารถทำงานร่วมกับแอปพลิเคชัน LINE Official Account เพื่อให้บริการตรวจจับรอยโรคข้าวสำคัญทางเศรษฐกิจ 5 ชนิด และให้คำปรึกษาการรักษาตามหลักวิชาการของกรมการข้าว กระทรวงเกษตรและสหกรณ์ แก่เกษตรกรได้อย่างสะดวก รวดเร็ว และแม่นยำ โดยมีการทำงานและผลการดำเนินงานของระบบตามกลุ่มผู้ใช้งานและส่วนประกอบหลัก ดังนี้

### 5.1.1 ผู้ใช้งานทั่วไป (เกษตรกรและผู้ปลูกข้าว)
ผู้ใช้งานทั่วไปสามารถเข้าถึงบริการผ่านแอปพลิเคชัน LINE บนโทรศัพท์มือถือ โดยการเพิ่มเพื่อนกับบัญชี LINE Official Account ของระบบ (`@325wtzzd`) โดยไม่ต้องติดตั้งแอปพลิเคชันอื่นเพิ่มเติม และสามารถทำรายการต่าง ๆ ได้ดังนี้:
1) สามารถเข้าถึงแถบเมนูลัด (Rich Menu Interface) บริเวณส่วนล่างของห้องสนทนา ซึ่งแบ่งเมนูอำนวยความสะดวกออกเป็น 4 หมวดหมู่หลัก ได้แก่
   1.1) เมนู "ถ่ายรูป/ส่งรูปเพื่อวินิจฉัยโรค" สำหรับเข้าสู่โหมดกล้องถ่ายภาพหรือเลือกภาพจากคลังภาพบนโทรศัพท์มือถือ
   1.2) เมนู "วิธีถ่ายภาพที่ถูกต้อง" สำหรับเปิดดูคำแนะนำในการถ่ายภาพใบข้าวให้ได้คุณภาพสูงและเพิ่มความแม่นยำในการวินิจฉัย
   1.3) เมนู "คู่มือโรคข้าว 5 ชนิด" สำหรับศึกษาข้อมูล ลักษณะอาการ และเชื้อสาเหตุของโรคข้าวสำคัญเบื้องต้น
   1.4) เมนู "สอบถามผู้เชี่ยวชาญ/ติดต่อเรา" สำหรับดูช่องทางการติดต่อเจ้าหน้าที่ส่งเสริมการเกษตรและฝ่ายพัฒนาระบบ
2) สามารถส่งภาพถ่ายใบข้าวที่มีอาการผิดปกติหรือมีรอยโรคเข้ามาในห้องสนทนาเพื่อทำการตรวจวินิจฉัย
3) สามารถรับผลลัพธ์การวินิจฉัยโรคเป็นภาพถ่ายใบข้าวที่มีการตีกรอบสี่เหลี่ยมระบุตำแหน่งรอยโรค (Bounding Box) พร้อมชื่อโรคภาษาไทยและระดับความมั่นใจของโมเดล (Confidence Score ในรูปแบบเปอร์เซ็นต์)
4) สามารถรับบัตรข้อความอัจฉริยะ (LINE Flex Message) ที่แสดงข้อมูลการวินิจฉัยและคำแนะนำการจัดการโรคอย่างครบวงจร ซึ่งประกอบด้วย:
   4.1) ชื่อโรคที่ตรวจพบ ทั้งภาษาไทยและภาษาอังกฤษ
   4.2) สาเหตุของโรค (เชื้อราหรือเชื้อแบคทีเรีย)
   4.3) ลักษณะอาการทางสัณฐานวิทยาของรอยโรค
   4.4) สารเคมีหรือสารชีวภัณฑ์ที่แนะนำในการควบคุมโรค พร้อมอัตราส่วนผสมต่อน้ำ 20 ลิตร ตามมาตรฐานของกรมการข้าว
   4.5) แนวทางการจัดการแปลงนา เช่น การจัดการน้ำ การปรับลดปุ๋ยไนโตรเจน และการกำจัดวัชพืชเพื่อตัดวงจรการระบาด
5) สามารถพิมพ์ข้อความคำถามเพิ่มเติมเป็นภาษาไทยธรรมชาติในห้องสนทนา เพื่อซักถามรายละเอียดเกี่ยวกับวิธีการใช้สารเคมี การดูแลรักษาแปลงนา หรือการควบคุมโรคเฉพาะกรณีได้ โดยระบบแชทบอทจะสืบค้นคำตอบจากฐานความรู้และตอบกลับอย่างตรงประเด็น
6) สามารถรับข้อความแจ้งเตือนความปลอดภัย (Safety Guardrail Message) ในกรณีที่ภาพถ่ายมีความสว่างน้อยเกินไป มีแสงสะท้อนจ้า หลุดโฟกัส หรือระดับความมั่นใจต่ำกว่า 30% เพื่อแนะนำให้ผู้ใช้ถ่ายภาพใหม่อย่างเหมาะสม

### 5.1.2 ผู้เชี่ยวชาญด้านโรคพืชและผู้ดูแลระบบ
ผู้เชี่ยวชาญและผู้ดูแลระบบสามารถกำกับดูแล ตรวจสอบความถูกต้อง และบริหารจัดการข้อมูลความรู้ของระบบได้ดังนี้:
1) สามารถตรวจสอบประวัติการส่งภาพและการตรวจวินิจฉัยโรคของผู้ใช้งานผ่านระบบบันทึกข้อมูล (Centralized Logging System) ได้อย่างละเอียด
2) สามารถเรียกดูสถิติการใช้งาน เช่น จำนวนภาพที่ส่งตรวจต่อวัน สัดส่วนการตรวจพบของแต่ละชนิดโรค และอัตราความมั่นใจเฉลี่ยของโมเดล
3) สามารถจัดการและอัปเดตเอกสารองค์ความรู้ในคลังความรู้มาตรฐาน (Knowledge Base) ของกรมการข้าว ผ่านกระบวนการแปลงเอกสารเป็นเวกเตอร์ความหมายลงในฐานข้อมูล Pinecone Vector Database เมื่อมีการปรับปรุงแนวทางการอารักขาพืชใหม่
4) สามารถตรวจสอบสถานะการทำงานของโครงสร้างพื้นฐาน ได้แก่ บริการ FastAPI Backend, Docker Container, n8n Workflow Router และการเชื่อมต่อ Webhook ของ LINE Messaging API
5) สามารถปรับตั้งค่าเกณฑ์ความมั่นใจในการตรวจจับ (Confidence Threshold) และเกณฑ์ความปลอดภัยของคำตอบ (Safety Guardrails) เพื่อให้สอดคล้องกับสภาพการณ์การระบาดของโรคในแต่ละฤดูกาล

### 5.1.3 การทำงานและประสิทธิภาพของระบบปัญญาประดิษฐ์
จากการดำเนินการวิจัยและทดลองอย่างเป็นระบบตามกระบวนการทางวิทยาศาสตร์คอมพิวเตอร์ ระบบสามารถทำผลงานเชิงประจักษ์ได้ดังนี้:

**1) ประสิทธิภาพของโมเดลตรวจจับโรคข้าว (RT-DETR-L Version 5)**
- โมเดล Real-Time Detection Transformer Large (RT-DETR-L v5) ซึ่งผ่านการฝึกฝนบนชุดข้อมูลภาพถ่ายใบข้าว 3,829 ภาพ ทำคะแนนเฉลี่ยบนชุดข้อมูลทดสอบ (Test Set) วัดค่า **$mAP@0.5$ สูงถึง 70.6% (0.7056)** โดยมีความแม่นยำรวม (Precision) **73.5%** และความครอบคลุมในการตรวจจับ (Recall) **70.2%**
- เมื่อพิจารณาประสิทธิภาพแยกตามรายชนิดโรค พบว่า:
  - โรคใบไหม้ (Leaf Blast: LB): มีคะแนน $mAP@0.5$ สูงที่สุดถึง **86.8%**
  - โรคใบจุดสีน้ำตาล (Brown Spot: BS): มีคะแนน $mAP@0.5$ อยู่ที่ **78.4%**
  - โรคใบขอบกาบแห้ง (Leaf Scald: LS): มีคะแนน $mAP@0.5$ อยู่ที่ **78.7%**
  - ตัวอย่างใบข้าวสมบูรณ์ (Healthy: H): มีคะแนน $mAP@0.5$ อยู่ที่ **64.9%**
  - โรคกาบใบแห้ง (Sheath Blight: ShB): มีคะแนน $mAP@0.5$ อยู่ที่ **45.4%** (เนื่องจากรอยโรคส่วนใหญ่เกิดขึ้นที่กาบใบด้านล่างติดระดับน้ำ)
  - โรคขอบใบแห้ง (Bacterial Leaf Blight: BLB): ทำคะแนน $mAP@0.5$ ได้ถึง **69.5%**
- ประสบความสำเร็จในการแก้ไขปัญหาจุดอ่อนเรื้อรังของโรคขอบใบแห้ง (BLB) ซึ่งในเวอร์ชัน 4 เคยได้คะแนนเพียง 7.42% ให้เพิ่มขึ้นก้าวกระโดดเป็น **69.50% (เพิ่มขึ้นถึง +62.1%)** ผ่านการประยุกต์ใช้กระบวนทัศน์ Data-Centric AI ด้วยการปรับปรุงฉลากข้อมูลแบบ Continuous Morphological Bounding Box จากเดิมที่แตกย่อยซ้ำซ้อน 5,922 กล่อง รวบเหลือ 1,863 กล่องที่ตรงตามสัณฐานวิทยาจริง
- ความเร็วในการอนุมานผล (Inference Latency) ของโมเดลบนการ์ดจอ NVIDIA GeForce RTX 4090 ใช้เวลาเพียง **6.8 มิลลิวินาทีต่อภาพ** (คิดเป็นอัตราความเร็วสูงถึงประมาณ 147 เฟรมต่อวินาที) ซึ่งรองรับการประมวลผลแบบ Real-Time ได้อย่างไร้รอยต่อ

**2) ผลการทดลองตัดพื้นหลังเชิงสัณฐานวิทยา (Ablation Study) และข้อค้นพบ Morphological Asymmetry**
- สามารถแก้ไขความล้มเหลวของโมเดลตัดฉากหลังอัตโนมัติดั้งเดิม (Salient Object Detection) ที่ทำให้ภาพกลายเป็นจอดำสนิทสูงถึง 43.8% ด้วยการนำโมเดลรากฐาน **Meta MobileSAM** ร่วมกับการนำร่องพิกัดกรอบสี่เหลี่ยม (Spatial Bounding Box Prompting) และนวัตกรรม **Adaptive Safety Guardrail ที่เกณฑ์ 2%** ทำให้อัตราความสำเร็จในการตัดพื้นหลังเพิ่มขึ้นเป็น **75.14%** โดยไม่มีภาพจอดำหลุดรอด
- ค้นพบข้อเท็จจริงทางสัณฐานวิทยาที่สำคัญ (**Morphological Asymmetry**): การตัดพื้นหลังแปลงนาช่วยเพิ่มคะแนนความแม่นยำให้กลุ่มแผลขนาดใหญ่ (Macro-lesions) เช่น โรคใบขอบกาบแห้ง (+11.17%) และโรคขอบใบแห้ง (+5.82%) แต่ส่งผลเสียอย่างรุนแรงต่อกลุ่มแผลจุดขนาดเล็กจิ๋ว (Micro-lesions) เช่น โรคใบจุดสีน้ำตาล (คะแนนดิ่งลง -15.19%) เนื่องจากการตัดพื้นหลังทำลายบริบทของเนื้อแผ่นใบไม้สีเขียวรอบรอยโรค
- จากข้อค้นพบดังกล่าว ผู้วิจัยจึงเลือกสถาปัตยกรรมการตรวจจับภาพเต็มโดยตรง (**Direct Detection ด้วย RT-DETR-L v5**) เป็นสถาปัตยกรรมหลักสำหรับระบบบริการจริง ซึ่งให้คะแนนเฉลี่ยสูงสุด มีความสมดุลทุกชนิดโรค และประหยัดทรัพยากรการประมวลผล

**3) ประสิทธิภาพระบบสืบค้นและตอบคำถามเชิงวิชาการ (Perfect Hybrid RAG Version 6)**
- ระบบค้นหาแบบผสมผสาน **Hybrid RAG V6** ผสานการค้นหาเชิงความหมาย (Dense Vector Search ผ่าน Google Gemini Embedding 3,072 มิติ) เข้ากับการค้นหาคำสำคัญเฉพาะทาง (Sparse BM25 ร่วมกับการตัดคำภาษาไทยด้วย **PyThaiNLP**) โดยใช้การถ่วงน้ำหนัก Alpha Blending ($\alpha = 0.7$) และการกรองข้อมูลด้วยชื่อโรค (Metadata Filtering)
- ผลการประเมินมาตรฐานด้วย RAGAS Framework บนชุดคำถามทดสอบ 70 ข้อ พบว่า:
  - **Context Recall:** อยู่ที่ **28.59%** (ค้นหาเอกสารสำคัญได้ครอบคลุมประเด็นคำถาม)
  - **Context Precision:** สูงถึง **51.05%** (จัดอันดับเอกสารคำตอบที่ตรงประเด็นไว้ในลำดับต้นได้อย่างแม่นยำ)
  - **Faithfulness:** อยู่ในเกณฑ์สูงมากถึง **76.50%** ซึ่งการันตีความซื่อสัตย์ต่อฐานข้อมูลวิชาการของกรมการข้าว และขจัดปัญหาการสร้างข้อมูลเท็จ (Hallucination) ในการแนะนำชื่อสารเคมีและอัตราส่วนผสมได้อย่างปลอดภัย

**4) ประสิทธิภาพการประมวลผลและการบูรณาการระบบแชทบอทบน LINE**
- เชื่อมต่อส่วนประกอบทั้งระบบอย่างสมบูรณ์แบบ ได้แก่ LINE Messaging API, n8n Workflow Automation, Docker Container และ FastAPI Backend v2
- ผ่านการทดสอบฟังก์ชันการทำงานจริงตามกรณีทดสอบ (Functional Test Cases TC-01 ถึง TC-08) ครบถ้วน **100% PASS (8/8 กรณี)**
- เวลาการตอบสนองรวมของระบบตั้งแต่ผู้ใช้งานส่งภาพผ่าน LINE จนได้รับข้อความตอบกลับผลการวินิจฉัย (End-to-End Latency) เฉลี่ยเพียง **1.68 วินาที** (โดยเป็นเวลาประมวลผลของ FastAPI Backend เพียง 0.82 วินาที) จัดอยู่ในเกณฑ์การให้บริการที่รวดเร็วทันทีทันใดบนโทรศัพท์มือถือ

**5) ผลการประเมินความพึงพอใจและการยอมรับของผู้ใช้งานจริง (User Acceptance Testing: UAT)**
- จากการประเมินผลการใช้งานระบบร่วมกับกลุ่มตัวอย่างผู้ใช้งานจริงจำนวน **30 ราย ($N=30$)** ประกอบด้วยเกษตรกรผู้ปลูกข้าว นักวิชาการเกษตร และผู้ใช้งานทั่วไป ด้วยแบบสอบถามมาตราส่วนประมาณค่า 5 ระดับ (Likert Scale)
- ผลการประเมินพบว่า **ดัชนีคะแนนความพึงพอใจเฉลี่ยรวม (Overall Satisfaction Index) อยู่ในระดับ "มากที่สุด" ที่ 4.58 / 5.00 ($S.D. = 0.53$)**
- หัวข้อที่ได้รับคะแนนความพึงพอใจสูงสุด ได้แก่ ความสะดวกและง่ายต่อการใช้งานผ่านแอปพลิเคชัน LINE ($\bar{X} = 4.67, S.D. = 0.48$) และความรวดเร็วในการประมวลผลและการตอบกลับ ($\bar{X} = 4.63, S.D. = 0.49$) ซึ่งยืนยันความพร้อมของระบบในการนำไปใช้งานจริงภาคสนาม

## 5.2 ปัญหาและอุปสรรค

ในการดำเนินงานวิจัยและพัฒนาระบบ คณะผู้พัฒนาได้พบปัญหาและอุปสรรคทางเทคนิคทั้งในด้านการเตรียมชุดข้อมูล การฝึกฝนโมเดลคอมพิวเตอร์วิทัศน์ การประมวลผลภาษาธรรมชาติ และการบูรณาการระบบเครือข่าย ซึ่งได้ทำการวิเคราะห์สาเหตุและดำเนินการแก้ไขจนระบบสามารถทำงานได้อย่างสมบูรณ์ โดยสามารถสรุปปัญหาและอุปสรรคสำคัญออกเป็น 5 ประเด็นหลัก ดังนี้:

### 5.2.1 ปัญหาด้านชุดข้อมูลและสัณฐานวิทยาของรอยโรค
1. **ปัญหาการแตกกระจายของกรอบสี่เหลี่ยมกำกับข้อมูล (Annotation Fragmentation) ในโรคขอบใบแห้ง:**
   - *ปัญหาที่พบ:* ในชุดข้อมูลดั้งเดิม โมเดลทำคะแนน $mAP@0.5$ ของโรคขอบใบแห้ง (BLB) ได้เพียง 7.42% แม้ว่าจะปรับจูนพารามิเตอร์ของโมเดลหลายรูปแบบแล้วก็ตาม
   - *สาเหตุ:* จากการตรวจสอบพบว่า ผู้ติดฉลากข้อมูลเดิมได้ตีกรอบสี่เหลี่ยมขนาดเล็กแตกกระจายซ้อนทับกันเป็นจำนวนมากถึง 5,922 กล่อง (เฉลี่ย 5–10 กล่องต่อหนึ่งรอยโรค) ขัดต่อสัณฐานวิทยาจริงของโรคที่เป็นปื้นยาวต่อเนื่องตามแนวขอบใบข้าว ทำให้โมเดล Transformer สับสนในการกำหนดขอบเขตแผล
   - *แนวทางการแก้ไข:* ประยุกต์ใช้กระบวนทัศน์ Data-Centric AI โดยดำเนินการปรับปรุงฉลากข้อมูลใหม่ (Re-labeling) รวบกล่องสี่เหลี่ยมที่แตกย่อยให้เป็นกรอบต่อเนื่องตามสัณฐานวิทยาจริง (Continuous Morphological Bounding Box) เหลือ 1,863 กล่องที่ถูกต้อง ทำให้คะแนน $mAP@0.5$ ของโรคขอบใบแห้งกระโดดขึ้นทันทีเป็น 69.50% (+62.1%)
2. **ปัญหาการสูญเสียลักษณะสัณฐานวิทยาจากเทคนิค Mosaic Data Augmentation:**
   - *ปัญหาที่พบ:* รอยโรคที่เป็นริ้วยาวและแคบตามขอบใบข้าวมีคะแนนการตรวจจับต่ำลงเมื่อเปิดใช้เทคนิค Mosaic
   - *สาเหตุ:* การย่อภาพ 4 ภาพมารวมกันในภาพเดียว ทำให้รอยโรคทรงแคบยาว (High Aspect Ratio) ถูกบีบย่อจนเหลือความกว้างเพียง 1–3 พิกเซล ซึ่งทำให้เลเยอร์ Attention ตีความผิดพลาดว่าเป็นสัญญาณรบกวน (Noise)
   - *แนวทางการแก้ไข:* ปรับแต่งวงรอบการฝึกฝนโดยการปิดเทคนิค Mosaic ในช่วง 10 รอบสุดท้าย (Close Mosaic Augmentation) เพื่อคืนรายละเอียดสัณฐานวิทยาจริงให้โมเดลได้เรียนรู้โครงสร้างขอบแผลได้อย่างแม่นยำ
3. **ปัญหาโมเดลตัดฉากหลังอัตโนมัติสร้างภาพจอดำสนิท (SOD Black Screen Failure):**
   - *ปัญหาที่พบ:* ในการทดลองตัดพื้นหลังแปลงนาด้วยโมเดล Salient Object Detection ทั่วไป (เช่น U-2-Net) พบภาพถูกลบจนกลายเป็นภาพสีดำสนิทสูงถึง 43.8% (155 จาก 354 ภาพ)
   - *สาเหตุ:* เกิดภาวะ Green-on-Green Failure เนื่องจากสีของใบข้าวกลืนไปกับฉากหลังของต้นข้าวอื่นในแปลงนา และใบข้าวพาดผ่านขอบภาพ (Edge-to-Edge Geometry) ทำให้ AI เข้าใจผิดว่าเป็นพื้นหลัง จึงลบภาพทิ้งทั้งหมด
   - *แนวทางการแก้ไข:* เปลี่ยนมาใช้โมเดลรากฐาน Meta MobileSAM ซึ่งรองรับการส่งพิกัด Bounding Box เป็นตัวนำทาง (Spatial Prompting) ทำให้โมเดลตัดเฉพาะใบข้าวเป้าหมายได้อย่างแม่นยำ
4. **ปัญหาการสูญเสียบริบทแผ่นใบของรอยโรคขนาดเล็ก (Context Loss) ในโมเดล SAM:**
   - *ปัญหาที่พบ:* เมื่อส่งพิกัดรอยโรคขนาดเล็ก (เช่น โรคใบจุดสีน้ำตาล ขนาด 10–30 พิกเซล) ให้โมเดล SAM ประมวลผล โมเดลจะตัดเฉพาะจุดแผลสีน้ำตาลออกมา แต่ลบเนื้อใบข้าวสีเขียวรอบข้างออกทั้งหมด
   - *สาเหตุ:* โมเดล SAM มองว่ารอยโรคขนาดเล็กเป็นวัตถุเอกเทศ (Independent Object) จึงสร้าง Mask เฉพาะจุดแผล ทำให้สูญเสียบริบทของแผ่นใบข้าว
   - *แนวทางการแก้ไข:* พัฒนาเทคนิค Enclosing Bounding Box Prompting โดยคำนวณหากรอบรวมของทุกรอยโรคบนใบข้าวพร้อมขยายขอบเขตออกไป (Padding +10 พิกเซล) ร่วมกับการกำหนด Centroid Point Prompting ช่วยกระตุ้นให้โมเดล SAM ขยายขอบเขตการตัดครอบคลุมแผ่นใบข้าวทั้งหมด
5. **ปัญหาเกณฑ์ความปลอดภัยของ Safety Guardrail ไม่สอดคล้องกับใบข้าวเดี่ยว:**
   - *ปัญหาที่พบ:* ใบข้าวที่มีสุขภาพดีหรือมีแผลเดี่ยวเรียวยาวถูกระบบเข้าใจผิดว่าเป็นภาพจอดำ และสั่งยกเลิกการตัดพื้นหลัง (Fallback) สูงถึง 70.3%
   - *สาเหตุ:* เกณฑ์ความปลอดภัยเดิมตั้งไว้ที่พื้นที่ Mask ต้องมากกว่า 5% ของภาพ (`mask_ratio < 0.05`) แต่ใบข้าวเดี่ยวที่พาดในแนวทแยงมีพื้นที่พิกเซลจริงเพียง 2.0%–4.9% ของพื้นที่ภาพทั้งหมด
   - *แนวทางการแก้ไข:* ปรับลดเกณฑ์ Safety Guardrail ลงสู่ค่า 2% (`mask_ratio < 0.02`) ส่งผลให้อัตราความสำเร็จในการตัดพื้นหลังเพิ่มขึ้นเป็น 75.14% โดยที่ยังคงป้องกันภาพจอดำได้อย่างสมบูรณ์ 100%
6. **ปัญหาภาพถ่ายใบข้าวสมบูรณ์ไม่มีกรอบกำกับตำแหน่ง (Zero-Annotation Issue):**
   - *ปัญหาที่พบ:* ภาพใบข้าวสมบูรณ์ (Healthy) ไม่มี Bounding Box ในไฟล์ Label ทำให้ไม่มี Prompt พิกัดส่งให้โมเดล SAM ตัดพื้นหลัง
   - *สาเหตุ:* คลาส Healthy เป็นภาพใบข้าวที่ไม่พบรอยโรค จึงไม่มีการตีกรอบ Bounding Box ในชุดข้อมูล
   - *แนวทางการแก้ไข:* พัฒนาฟังก์ชัน `find_prominent_vegetation_bbox()` โดยแปลงภาพเข้าสู่ระบบสี HSV และตรวจจับคอนทัวร์ของกลุ่มพืชสีเขียวที่มีขนาดใหญ่ที่สุดในภาพ เพื่อสร้าง Bounding Box เสมือนส่งเป็น Prompt ให้ SAM อัตโนมัติ ช่วยให้อัตราการตัดพื้นหลังของภาพ Healthy สำเร็จสูงถึง 88.1%

### 5.2.2 ปัญหาด้านวิศวกรรมการฝึกฝนโมเดลและข้อจำกัดทรัพยากรฮาร์ดแวร์
1. **ปัญหาหน่วยความจำหลักของระบบล้นจนโปรแกรมหยุดทำงาน (RAM OOM-Killer Crash):**
   - *ปัญหาที่พบ:* ในการฝึกฝนโมเดลที่ความละเอียดภาพ $800 \times 800$ พิกเซล โปรแกรมหยุดทำงานกะทันหันบนระบบปฏิบัติการ Linux ด้วย Exit Code 137 (SIGKILL)
   - *สาเหตุ:* การตั้งค่า `cache='ram'` ร่วมกับจำนวน Dataloader Workers 16 โพรเซส ทำให้หน่วยความจำหลัก (RAM) ถูกจองใช้งานพุ่งสูงทะลุ 64 GB ในเวลาไม่กี่วินาที จนเคอร์เนลของระบบปฏิบัติการต้องสั่งยุติโปรแกรมเพื่อป้องกันระบบล่ม
   - *แนวทางการแก้ไข:* เปลี่ยนรูปแบบการแคชข้อมูลจากการโหลดลง RAM มาเป็น `cache='disk'` โดยระบบจะแปลงภาพและแคชเป็นไฟล์ไบนารี (`.npy`) บนไดรฟ์ความเร็วสูง NVMe SSD ทำให้การใช้งาน RAM ลดลงเหลือเพียง 6–8 GB และคงประสิทธิภาพการส่งข้อมูลให้การ์ดจอ RTX 4090 ได้อย่างต่อเนื่อง (GPU Utilization 96%)
2. **ปัญหาการแตกโพรเซสย่อยไม่สิ้นสุดของ PyTorch บน Linux (Infinite Multiprocessing):**
   - *ปัญหาที่พบ:* โปรแกรมแจ้งข้อผิดพลาด `RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase`
   - *สาเหตุ:* การทำงานแบบ Multiprocessing ของ PyTorch Dataloader บน Linux จำเป็นต้องมีการแบ่งขอบเขตการทำงานของสคริปต์หลักออกจากโพรเซสย่อยให้ชัดเจน
   - *แนวทางการแก้ไข:* จัดโครงสร้างโค้ดให้อยู่ภายใต้กรอบคำสั่ง `if __name__ == '__main__':` และสร้างฟังก์ชัน `main()` เพื่อแยกจุดเริ่มต้นการประมวลผลหลักอย่างชัดเจน
3. **ปัญหาภาระการคำนวณที่เพิ่มขึ้นแบบกำลังสองใน Vision Transformer:**
   - *ปัญหาที่พบ:* เมื่อขยายขนาดภาพนำเข้าจาก 640 พิกเซลเป็น 800 พิกเซล ความเร็วในการฝึกฝนต่อ Epoch ลดลงเกือบเท่าตัว
   - *สาเหตุ:* จำนวน Token ในโครงสร้าง Multi-Scale Self-Attention เพิ่มขึ้นจาก 400 เป็น 625 จุด ส่งผลให้ภาระการคำนวณ Attention Matrix เพิ่มขึ้น 2.44 เท่า (ค่า GFLOPs เพิ่มขึ้นจาก 105 เป็น 170 GFLOPs)
   - *แนวทางการแก้ไข:* เปิดใช้งานคำสั่ง `torch.backends.cudnn.benchmark = True` เพื่อให้ CUDA ทำการเลือกอัลกอริทึม Convolution และ Matrix Multiplication ที่เร็วและเหมาะสมที่สุดกับสถาปัตยกรรมฮาร์ดแวร์โดยอัตโนมัติ
4. **ปัญหาข้อความแจ้งเตือนสีแดงซ้ำซ้อนจาก CUDA Grid Sampler:**
   - *ปัญหาที่พบ:* หน้าจอคอนโซลแสดงข้อความเตือน `UserWarning: grid_sampler_2d_backward_cuda does not have a deterministic implementation` ซ้ำ ๆ ทุก Epoch
   - *สาเหตุ:* ฟังก์ชัน Grid Sampler ของโมเดล RT-DETR ทำงานแบบ Atomic Operations บน CUDA ซึ่งมีความไม่แน่นอนในระดับไมโครวินาที (Non-deterministic) จึงมีการแจ้งเตือนทางสถิติ
   - *แนวทางการแก้ไข:* ใส่คำสั่งกรองข้อความเตือน `warnings.filterwarnings("ignore")` และตั้งค่าพารามิเตอร์ `deterministic=False` ในการฝึกฝน เพื่อให้การ์ดจอประมวลผลด้วยความเร็วสูงสุดโดยไม่หยุดชะงัก
5. **ปัญหาการค้นหาพาธชุดข้อมูลไม่พบจาก Relative Directory Execution:**
   - *ปัญหาที่พบ:* การสั่งรันสคริปต์การฝึกฝนจากเทอร์มินัลในคนละโฟลเดอร์ ส่งผลให้เกิดข้อผิดพลาด `FileNotFoundError: dataset.yaml not found`
   - *สาเหตุ:* การใช้พาธแบบสัมพัทธ์ (Relative Path) ในสคริปต์ ทำให้เมื่อเรียกใช้งานจาก CWD อื่น โปรแกรมไม่สามารถระบุตำแหน่งที่ตั้งจริงของไฟล์ข้อมูลได้
   - *แนวทางการแก้ไข:* เพิ่มคำสั่ง `os.chdir(os.path.dirname(os.path.abspath(__file__)))` ที่ส่วนต้นของทุกสคริปต์ และเขียนฟังก์ชัน Recursive Search (`**/{prefix}*/weights/best.pt`) เพื่อค้นหาและโหลดไฟล์น้ำหนักโมเดลล่าสุดได้อย่างถูกต้องและอัตโนมัติ

### 5.2.3 ปัญหาด้านการประมวลผลภาษาธรรมชาติและระบบสืบค้นข้อมูลเชิงวิชาการ (RAG)
1. **ปัญหาอัลกอริทึม Regular Expression ทำลายคำศัพท์ภาษาไทยในอัลกอริทึม BM25:**
   - *ปัญหาที่พบ:* ระบบค้นหาแบบ Sparse BM25 ไม่สามารถค้นหาเอกสารคำตอบภาษาไทยได้ถูกต้อง คะแนนความตรงประเด็นต่ำมาก
   - *สาเหตุ:* โค้ดดั้งเดิมใช้ Regular Expression `[\w]+` ซึ่งอิงตามภาษาอังกฤษที่มีการเว้นวรรคระหว่างคำ เมื่อนำมาใช้กับภาษาไทยที่เขียนคำติดกัน ส่งผลให้คำศัพท์ถูกหั่นเป็นเศษอักษรที่ไม่มีความหมาย เช่น `['โรคใบจ', 'ดส']`
   - *แนวทางการแก้ไข:* บูรณาการไลบรารีตัดคำภาษาไทย **`PyThaiNLP` (`word_tokenize`)** เข้ามาใช้ในกระบวนการ Tokenization ของอัลกอริทึม BM25 ทำให้สามารถตัดคำศัพท์ทางการเกษตรและชื่อโรคภาษาไทยได้อย่างถูกต้อง 100%
2. **ปัญหาสเกลคะแนนความถี่คำซ้ำซ้อน (Double IDF Scoring) กลบการค้นหาเชิงความหมาย:**
   - *ปัญหาที่พบ:* การค้นหาแบบ Hybrid Search ถูกครอบงำด้วยคีย์เวิร์ดอย่างสิ้นเชิง และไม่นำผลลัพธ์เชิงความหมายของโมเดล Gemini มาพิจารณา
   - *สาเหตุ:* โค้ดมีการคูณค่า Inverse Document Frequency (IDF) ซ้ำซ้อนทั้งในขั้นตอนทำดัชนีเอกสารและขั้นตอนส่งคำค้นหา เมื่อทำ Dot Product ทำให้ค่า IDF ถูกยกกำลังสอง ส่งผลให้คะแนนฝั่ง Sparse สูงถึง 10–50 ในขณะที่คะแนนฝั่ง Dense อยู่ที่เพียง 0.6–1.0
   - *แนวทางการแก้ไข:* ปรับสมการคณิตศาสตร์ของ BM25 ให้บันทึกเฉพาะค่า `TF_norm` ในเอกสาร และนำค่า IDF ไปคูณเฉพาะฝั่งคำค้นหาตามมาตรฐานสากล พร้อมพัฒนาฟังก์ชัน **Alpha Blending ($\alpha = 0.7$)** เพื่อปรับสเกลคะแนนให้อยู่ในช่วงมาตรฐานร่วมกัน โดยให้น้ำหนักความหมาย (Dense) 70% และน้ำหนักคำสำคัญ (Sparse) 30%
3. **ปัญหาการติดตั้งไลบรารี `pinecone-text` ล้มเหลวบนระบบปฏิบัติการ Windows:**
   - *ปัญหาที่พบ:* ไม่สามารถติดตั้งแพ็กเกจ `pinecone-text` ผ่านคำสั่ง `pip install` บน Windows ได้
   - *สาเหตุ:* ไลบรารีดังกล่าวต้องการคอมไพเลอร์ C++ (Microsoft Visual C++ Build Tools) ในการคอมไพล์โค้ด ซึ่งสภาพแวดล้อมบนเครื่องพัฒนาไม่มีซอฟต์แวร์ดังกล่าวติดตั้งอยู่
   - *แนวทางการแก้ไข:* ออกแบบและพัฒนาโมดูลคำนวณ Sparse Vector (BM25) ขึ้นเองโดยตรง (Manual Implementation) โดยนำไลบรารี `mmh3` มาใช้ทำ MurmurHash และจัดเก็บสถิติความถี่คำลงในไฟล์ `bm25_stats.json` ทำให้ระบบสามารถทำงานได้ทันทีโดยไม่ต้องพึ่งพา C++ Build Tools
4. **ปัญหาความไม่ตรงกันของมิติเวกเตอร์ (Dimension Mismatch) ระหว่างโมเดลกับฐานข้อมูล Pinecone:**
   - *ปัญหาที่พบ:* เกิดข้อผิดพลาด `Dimension mismatch: Index expects 768 dimensions, but vector has 3072 dimensions` ขณะอัปโหลดข้อมูล
   - *สาเหตุ:* ดัชนีเดิมใน Pinecone ถูกสร้างไว้สำหรับโมเดลขนาด 768 มิติ แต่โมเดล Google `gemini-embedding-001` เวอร์ชันที่ใช้งานสร้างเวกเตอร์ความยาว 3,072 มิติ
   - *แนวทางการแก้ไข:* อัปเดตไลบรารี `pinecone` เป็นเวอร์ชันล่าสุด พร้อมเขียนสคริปต์ลบ Index เดิมและสร้าง Index ใหม่ที่รองรับขนาด 3,072 มิติ และใช้ฟังก์ชันวัดระยะทางแบบ Cosine Similarity ได้อย่างถูกต้อง
5. **ปัญหา Information Overload และภาวะ Lost in the Middle ของโมเดลภาษาขนาดใหญ่:**
   - *ปัญหาที่พบ:* ในการประเมิน RAGAS ค่า Context Recall ตกต่ำลงเมื่อขยายขนาดของเอกสารอ้างอิงให้ยาวขึ้น
   - *สาเหตุ:* เมื่อเอกสารมีขนาดยาวเกินไป โมเดล LLM จะให้ความสนใจเฉพาะข้อมูลส่วนต้นและส่วนท้ายของข้อความ ทำให้มองข้ามข้อมูลสำคัญที่อยู่ตรงกลางเอกสาร
   - *แนวทางการแก้ไข:* ปรับปรุงขนาดการแบ่งชิ้นข้อมูล (Chunking Strategy) สู่จุดสมดุลที่ Chunk Size 1,500 ตัวอักษร และ Overlap 300 ตัวอักษร ร่วมกับเทคนิค Context Enrichment โดยใส่ชื่อโรคกำกับไว้ที่หัวเอกสารทุกชิ้น และใช้ Metadata Filtering กรองค้นหาเฉพาะเอกสารของโรคที่ตรวจพบ ตัดข้อมูลรบกวนออกได้ 100%
6. **ปัญหาการแสดงผลภาษาไทยผิดพลาด (UnicodeEncodeError) บนคอนโซล Windows:**
   - *ปัญหาที่พบ:* สคริปต์การทดสอบแครชและหยุดทำงานด้วยข้อผิดพลาด `'charmap' codec can't encode characters in position ...: character maps to <undefined>`
   - *สาเหตุ:* ระบบปฏิบัติการ Windows มีการตั้งค่าการแสดงผลคอนโซลเริ่มต้นเป็นรหัสภาษาไทยเฉพาะถิ่น (cp874 หรือ cp1252) ซึ่งไม่รองรับอักขระ UTF-8 สากล
   - *แนวทางการแก้ไข:* เพิ่มคำสั่ง `sys.stdout.reconfigure(encoding='utf-8')` และเปิดใช้ `line_buffering=True` ที่ส่วนต้นของทุกสคริปต์ ทำให้แสดงผลข้อความภาษาไทยและหลอดแสดงความคืบหน้า (Progress Bar) ได้อย่างถูกต้องและต่อเนื่อง

### 5.2.4 ปัญหาด้านการประเมินผลอัตโนมัติและข้อจำกัดการเรียกใช้ API ภายนอก
1. **ปัญหาการชนเพดานข้อจำกัดคำขอ (Rate Limit & Error 429) ในการประเมิน RAGAS:**
   - *ปัญหาที่พบ:* การรันประเมินผลคำถาม 70 ข้อผ่าน RAGAS ต้องเรียกใช้งาน API รวมกว่า 280 ครั้ง ทำให้ติดเพดานข้อจำกัดโควตา (Rate Limit 429) ของ Google Gemini API และหยุดทำงานกลางคันที่ข้อที่ 23
   - *สาเหตุ:* บัญชีประเภท Free Tier ของ Gemini มีข้อจำกัดอัตราคำขอต่อนาที (RPM) และคำขอต่อวัน (RPD)
   - *แนวทางการแก้ไข:* พัฒนาระบบประเมินผลแบบแยกส่วน (Decoupled Evaluator) โดยสลับมาใช้โมเดล DeepSeek ผ่าน OpenCodeZen ซึ่งให้โควตาและอัตราการตอบสนองที่สูงกว่า มาทำหน้าที่เป็นกรรมการตรวจคำตอบ (LLM as a Judge) แทน
2. **ปัญหา RAGAS พยายามเชื่อมต่อ OpenAI API โดยอัตโนมัติ (Provider Mismatch):**
   - *ปัญหาที่พบ:* โมดูล RAGAS แจ้งเตือนข้อผิดพลาด `openai.OpenAIError: The api_key client option must be set`
   - *สาเหตุ:* ค่าเริ่มต้นของ RAGAS ถูกกำหนดไว้สำหรับเชื่อมต่อกับ OpenAI API
   - *แนวทางการแก้ไข:* กำหนดการส่งผ่านออบเจกต์ LLM และ Embeddings ของผู้ให้บริการที่ต้องการเข้าไปยังฟังก์ชัน `evaluate()` ของ RAGAS โดยตรง และตั้งค่า `max_workers=1` เพื่อควบคุมความถี่ในการส่งคำขอให้อยู่ในเกณฑ์ที่ปลอดภัย
3. **ปัญหาข้อผิดพลาด Bad Request จากการสร้างคำถามย้อนกลับ (Strictness Mismatch):**
   - *ปัญหาที่พบ:* การประเมินเมทริก Answer Relevancy ล้มเหลวและส่งผลคะแนนเป็น `NaN`
   - *สาเหตุ:* RAGAS มีค่าเริ่มต้นในการสร้างคำถามย้อนกลับ 3 คำถาม (`n=3`) แต่ API ของโมเดล DeepSeek รองรับการสร้างคำตอบเพียงชุดเดียว (`n=1`) ต่อหนึ่งคำขอ
   - *แนวทางการแก้ไข:* ปรับแต่งค่าคุณสมบัติ `answer_relevancy.strictness = 1` เพื่อบังคับให้สร้างคำถามย้อนกลับเพียง 1 ชุด ทำให้ระบบสามารถรันประเมินผลได้อย่างต่อเนื่องโดยไม่เกิด BadRequestError
4. **ปัญหาความไม่เสถียรของเครือข่ายภายนอก (Timeout & Service Busy Error 503):**
   - *ปัญหาที่พบ:* ในการประเมินผลต่อเนื่องเป็นเวลานาน บางข้อคำถามเกิดอาการ Timeout หรือ Error 503 จากเซิร์ฟเวอร์ภายนอก ทำให้ผลคะแนนกลายเป็นค่าว่าง (`NaN`)
   - *สาเหตุ:* ความหนาแน่นของการเรียกใช้งาน API สากลในช่วงเวลาที่มีผู้ใช้บริการพร้อมกันสูง
   - *แนวทางการแก้ไข:* กำหนดพารามิเตอร์ `raise_exceptions=False` ในการประเมินเพื่อป้องกันไม่ให้โปรแกรมแครช และพัฒนาสคริปต์สำหรับตรวจสอบและซ่อมแซมคะแนน (`03_fix_evaluate_scores.py`) เพื่อค้นหาเฉพาะข้อที่มีค่าเป็น `NaN` แล้วทำการส่งประเมินซ่อมแซมเฉพาะข้อที่ผิดพลาดจนครบถ้วนทั้ง 70 ข้อโดยไม่ต้องเริ่มใหม่ทั้งหมด
5. **ปัญหาข้อผิดพลาด `KeyError: 0` ขณะบันทึกผลลัพธ์ RAGAS:**
   - *ปัญหาที่พบ:* หลังจากรันประเมินผลจนครบ 70 ข้อ โปรแกรมแครชขณะพยายามแปลงผลลัพธ์ด้วยคำสั่ง `dict(s)` ทำให้เสี่ยงต่อการสูญหายของผลการทดลอง
   - *สาเหตุ:* ไลบรารี RAGAS เวอร์ชันใหม่ได้ปรับปรุงโครงสร้างภายในของคลาส `EvaluationResult` ทำให้ไม่รองรับการแปลงเป็นดิกชันนารีโดยตรง
   - *แนวทางการแก้ไข:* เปลี่ยนวิธีการส่งออกข้อมูลมาใช้เมธอด `s.to_pandas()` แปลงผลลัพธ์เป็นตาราง DataFrame บันทึกลงไฟล์ `.csv` ทันที พร้อมเขียนฟังก์ชันคำนวณค่าเฉลี่ยของแต่ละเมทริกเพื่อบันทึกลงในไฟล์ `.json` ได้อย่างสมบูรณ์

### 5.2.5 ปัญหาด้านการบูรณาการระบบและบริการแชทบอทบนเครือข่าย
1. **ปัญหาการสื่อสารข้ามเครือข่ายระหว่าง n8n Docker และ FastAPI Host (Connection Refused):**
   - *ปัญหาที่พบ:* โหนด HTTP Request ของ n8n ซึ่งทำงานอยู่ภายใน Docker Container ไม่สามารถเชื่อมต่อกับ FastAPI Backend ที่รันอยู่บนเครื่องโฮสต์ (`http://localhost:8000`) ได้
   - *สาเหตุ:* ภายใน Docker Container คำว่า `localhost` จะหมายถึงตัวคอนเทนเนอร์เอง ไม่ได้หมายถึงเครื่องโฮสต์ภายนอก
   - *แนวทางการแก้ไข:* เพิ่มการตั้งค่า `extra_hosts: ["host.docker.internal:host-gateway"]` ในไฟล์ `docker-compose.yml` และเปลี่ยนเป้าหมาย URL ใน n8n เป็น `http://host.docker.internal:8000` ทำให้คอนเทนเนอร์สามารถเรียกใช้ FastAPI บนโฮสต์ได้อย่างสมบูรณ์
2. **ปัญหาการขึ้นบรรทัดใหม่ทำให้โครงสร้าง JSON เสียหาย (Bad Control Characters):**
   - *ปัญหาที่พบ:* แชทบอท LINE ไม่ตอบกลับข้อความคำแนะนำที่มีความยาวหลายบรรทัด และ n8n แจ้งเตือนข้อผิดพลาด `Bad control character in string literal`
   - *สาเหตุ:* ข้อความคำแนะนำการรักษาโรคมีอักขระขึ้นบรรทัดใหม่ (`\n`) และเครื่องหมายคำพูด เมื่อนำมาประกบสตริงใน JSON Body ของโหนด LINE โดยตรง ทำให้อักขระพิเศษเหล่านี้ทำลายโครงสร้างของ JSON
   - *แนวทางการแก้ไข:* ปรับแต่ง Expression ใน n8n โดยใช้ฟังก์ชัน `JSON.stringify({...})` ครอบ Payload ทั้งหมด เพื่อทำการแปลงอักขระพิเศษ (Escape Characters) ตามมาตรฐานสากลก่อนส่งไปยัง LINE API
3. **ปัญหาการดาวน์โหลดรูปภาพจาก LINE API ล้มเหลวด้วยข้อผิดพลาด 401 Unauthorized:**
   - *ปัญหาที่พบ:* ระบบ n8n ไม่สามารถดึงไฟล์รูปภาพที่เกษตรกรส่งมาจากเซิร์ฟเวอร์ของ LINE ได้
   - *สาเหตุ:* โหนด HTTP Request ของ n8n เวอร์ชันใหม่มีค่าเริ่มต้นไม่ส่ง Header การอนุญาตหากไม่มีการเปิดใช้งานอย่างชัดเจน
   - *แนวทางการแก้ไข:* เพิ่มคอนฟิก `"sendHeaders": true` และ `"specifyHeaders": "keypair"` ในโครงสร้าง Workflow พร้อมระบุ Header `Authorization: Bearer <Channel_Access_Token>` ทำให้ระบบสามารถดึงไฟล์ภาพมาประมวลผลต่อได้อย่างราบรื่น

## 5.3 ข้อเสนอแนะ

จากผลการดำเนินงาน การทดสอบระบบ และบทเรียนที่ได้รับจากการวิจัย คณะผู้พัฒนาขอเสนอแนะแนวทางปฏิบัติที่เป็นประโยชน์ต่อการนำระบบไปใช้งานจริงในแปลงนาและการดูแลรักษาระบบ ดังนี้:

### 5.3.1 ด้านการบันทึกภาพถ่ายของเกษตรกรในแปลงนา
1. **ระยะห่างและตำแหน่งในการถ่ายภาพ:** เกษตรกรควรถ่ายภาพใบข้าวในระยะใกล้ (Close-up) ประมาณ 15–30 เซนติเมตร โดยจัดให้แผ่นใบข้าวที่เป็นโรคพาดผ่านกึ่งกลางภาพ เพื่อให้โมเดลได้รับรายละเอียดของรอยโรคอย่างคมชัด หลีกเลี่ยงการถ่ายภาพมุมกว้างทั้งกอข้าวหรือทั้งแปลงนา เนื่องจากจะทำให้รอยโรคมีขนาดเล็กเกินกว่าที่ระบบจะตรวจจับได้
2. **การจัดการสภาวะแสง:** ควรหลีกเลี่ยงการถ่ายภาพย้อนแสงแดดโดยตรง หรือการถ่ายภาพในขณะที่มีแสงแดดจ้าสะท้อนผิวน้ำในแปลงนาจนเกิดแสงสะท้อน (Sun Glare) หากแสงแดดจ้าเกินไป แนะนำให้ใช้เงาของร่างกายหรือหมวกช่วยบังแสง เพื่อให้สีของรอยโรคมีความเป็นธรรมชาติและสม่ำเสมอ
3. **การส่งภาพตรวจสอบหลายมุมมอง:** ในกรณีที่ต้นข้าวมีอาการผิดปกติที่ยังไม่ชัดเจน หรือสงสัยว่าเกิดโรคระบาดร่วมกันหลายชนิด ควรส่งภาพถ่ายใบข้าว 2–3 ภาพจากมุมที่ต่างกัน เพื่อให้ระบบทำการตรวจวินิจฉัยและยืนยันผลได้อย่างแม่นยำยิ่งขึ้น

### 5.3.2 ด้านการบริหารจัดการทรัพยากรระบบและโควตา API
1. **การติดตั้งระบบแคชข้อมูลความหมาย (Semantic Caching):** สำหรับคำถามที่มีการสอบถามซ้ำบ่อยครั้ง เช่น "โรคไหม้ใช้ยาอะไร" หรือ "อัตราผสมสารไตรไซคลาโซล" ผู้ดูแลระบบควรติดตั้งระบบ Semantic Cache (เช่น Redis) เพื่อจัดเก็บคำถามและคำตอบที่ผ่านการตรวจทานแล้วไว้ในหน่วยความจำ เมื่อมีผู้ใช้สอบถามซ้ำ ระบบสามารถดึงคำตอบส่งกลับได้ทันทีโดยไม่ต้องเรียกใช้บริการ LLM API ภายนอก ซึ่งจะช่วยลดค่าใช้จ่ายด้าน API ได้มากกว่า 50% และลดเวลาการตอบสนองลงเหลือน้อยกว่า 0.5 วินาที
2. **การใช้งานเครือข่ายและโดเมนแบบคงที่ (Production Webhook Infrastructure):** ในการใช้งานจริงระดับองค์กรหรือแปลงใหญ่ ควรย้ายจากการใช้บริการชั่วคราว (Tunneling) ไปสู่การติดตั้ง Reverse Proxy (เช่น Nginx) ร่วมกับคลาวด์เซิร์ฟเวอร์ที่มี Public IP คงที่ และติดตั้งใบรับรองความปลอดภัย SSL/TLS ที่ถูกต้อง เพื่อป้องกันปัญหา Webhook URL หลุดหรือหมดอายุเมื่อรีสตาร์ตเซิร์ฟเวอร์

### 5.3.3 ด้านการรักษาความปลอดภัยและความถูกต้องของคำแนะนำทางวิชาการ
1. **การรักษาเกณฑ์ความปลอดภัยของคำตอบ (Faithfulness Guardrails):** ในการปรับปรุงหรือเปลี่ยนผ่านโมเดลภาษาในอนาคต ผู้ดูแลระบบจะต้องกำหนดให้ระบบอ้างอิงข้อมูลจากคลังเอกสารของกรมการข้าวเท่านั้น ห้ามอนุญาตให้โมเดลตอบคำถามเกี่ยวกับชื่อสารเคมีและอัตราส่วนผสมจากความทรงจำภายนอก (Unconstrained Pre-trained Knowledge) โดยเด็ดขาด เพื่อป้องกันความเสียหายต่อผลผลิตทางการเกษตรและสิ่งแวดล้อม
2. **การคงค่าเกณฑ์ความมั่นใจในการตรวจจับ (Confidence Threshold):** ควรกำหนดเกณฑ์ความมั่นใจขั้นต่ำของการตรวจจับรอยโรคไว้ที่ 30%–40% หากโมเดลตรวจพบรอยโรคแต่มีค่าความมั่นใจต่ำกว่าเกณฑ์ดังกล่าว ระบบควรส่งข้อความแนะนำให้ผู้ใช้ถ่ายภาพใหม่อีกครั้ง แทนการฝืนคาดเดาผลการวินิจฉัย

## 5.4 แนวทางในการพัฒนาต่อ

ในปัจจุบัน ระบบเชี่ยวชาญเพื่อการวินิจฉัยโรคพืชในข้าวสามารถให้บริการตรวจจับโรคข้าวสำคัญ 5 ชนิด และให้คำแนะนำการรักษาผ่านแอปพลิเคชัน LINE ได้อย่างมีประสิทธิภาพ อย่างไรก็ตาม เพื่อยกระดับความสามารถของระบบให้ครอบคลุม ก้าวหน้า และตอบโจทย์เกษตรกรรมแม่นยำ (Smart Agriculture) ยิ่งขึ้น คณะผู้พัฒนาขอเสนอแนวทางในการพัฒนาต่อยอดในอนาคต ดังต่อไปนี้:

### 5.4.1 การเชื่อมต่อกับอากาศยานไร้คนขับ (UAV) และอุปกรณ์ Edge AI ในแปลงนา
ในปัจจุบัน ระบบยังต้องพึ่งพาการถ่ายภาพรายต้นจากสมาร์ทโฟนของเกษตรกร แนวทางในการพัฒนาต่อคือ การนำโมเดล RT-DETR-L v5 ไปแปลงและบีบอัดด้วย TensorRT (INT8/FP16 Quantization) เพื่อนำไปติดตั้งบนคอมพิวเตอร์บอร์ดเดี่ยวขนาดเล็ก (เช่น NVIDIA Jetson Orin Nano) ที่ติดตั้งอยู่บนอากาศยานไร้คนขับเพื่อการเกษตร (Agricultural Drone) ทำให้สามารถบินสำรวจแปลงนาข้าวในระดับความสูงต่ำเพื่อถ่ายภาพ บันทึกพิกัด GPS และประมวลผลตรวจจับการระบาดของโรคข้าวได้แบบ Real-time พร้อมสร้างแผนที่ความเสี่ยงการระบาดของโรค (Disease Distribution Heatmap) ระดับแปลงนาได้อย่างรวดเร็ว

### 5.4.2 การพัฒนาระบบสืบค้นออฟไลน์ด้วยแบบจำลองภาษาขนาดเล็ก (Small Language Models: SLM)
เพื่อแก้ไขข้อจำกัดด้านสัญญาณเครือข่ายอินเทอร์เน็ตในพื้นที่เกษตรกรรมห่างไกล แนวทางในการพัฒนาต่อคือ การวิจัยและประยุกต์ใช้แบบจำลองภาษาขนาดเล็ก (Small Language Models เช่น Gemma-2B-Thai, LLaMA-3-8B หรือ Typhoon ที่ผ่านการ Quantization ระดับ 4-bit) และฐานข้อมูลเวกเตอร์แบบฝังตัว (เช่น ChromaDB หรือ SQLite-VSS) เพื่อติดตั้งและประมวลผลแบบออฟไลน์ (Offline Edge Inference) บนเครื่องคอมพิวเตอร์ประจำศูนย์ส่งเสริมและถ่ายทอดเทคโนโลยีการเกษตรประจำตำบล หรือสหกรณ์การเกษตรในพื้นที่ ทำให้เกษตรกรสามารถนำอุปกรณ์มารับบริการได้โดยไม่ต้องพึ่งพาสัญญาณอินเทอร์เน็ต

### 5.4.3 การพัฒนาระบบการเรียนรู้ต่อเนื่องจากผลตอบรับของผู้ใช้งาน (Continuous Active Learning)
แนวทางในการพัฒนาต่อคือ การเพิ่มปุ่มโต้ตอบบนบัตรข้อความ LINE Flex Message เพื่อให้เกษตรกรหรือเจ้าหน้าที่ส่งเสริมการเกษตรสามารถกด "ยืนยันผลถูกต้อง" หรือ "รายงานผลคลาดเคลื่อน" พร้อมระบุความคิดเห็นหรือแนบภาพถ่ายเพิ่มเติม ภาพถ่ายที่ได้รับการรายงานว่าคลาดเคลื่อนหรือภาพที่มีค่าความมั่นใจต่ำ (Uncertain Samples) จะถูกส่งเข้าสู่คลังจัดเก็บข้อมูลอัตโนมัติ (Active Learning Queue) เพื่อให้นักวิชาการโรคพืชทำการตรวจสอบและแก้ไขฉลากข้อมูล จากนั้นระบบจะนำข้อมูลดังกล่าวไปฝึกฝนโมเดลซ้ำ (Continual Fine-Tuning) เป็นรอบระยะเวลา เช่น ทุกไตรมาส ซึ่งจะช่วยให้ระบบมีวิวัฒนาการความแม่นยำสูงขึ้นอย่างต่อเนื่องตามกาลเวลา

### 5.4.4 การขยายขอบเขตการจำแนกโรคข้าวเพิ่มเติมและระยะการเจริญเติบโตของพืช
ในระยะต่อไป ควรขยายการรวบรวมชุดข้อมูลและฝึกฝนโมเดลให้ครอบคลุมโรคข้าวชนิดอื่น ๆ เพิ่มเติม เช่น โรคที่เกิดจากเชื้อไวรัส (โรคใบสีส้ม, โรคใบหงิก) โรคดอกกระถิน (False Smut) รวมถึงการตรวจจับแมลงศัตรูพืชสำคัญ เช่น เพลี้ยกระโดดสีน้ำตาล และหนอนกอข้าว นอกจากนี้ ควรพัฒนาโมเดลให้สามารถจำแนกระยะการเจริญเติบโตของต้นข้าว (เช่น ระยะกล้า ระยะแตกกอ ระยะตั้งท้อง และระยะออกรวง) เพื่อให้ระบบ RAG สามารถให้คำแนะนำการใส่ปุ๋ยและการดูแลรักษาแปลงนาที่สอดคล้องกับช่วงอายุของต้นข้าวได้อย่างเฉพาะเจาะจงและสมบูรณ์แบบมากยิ่งขึ้น
