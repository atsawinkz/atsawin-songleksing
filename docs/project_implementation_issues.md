# สรุปปัญหาและวิธีการแก้ไขในระหว่างการพัฒนาโปรเจกต์ (Project Implementation Issues)

ในกระบวนการพัฒนาระบบแชทบอทวินิจฉัยโรคข้าว (ทั้งในส่วนของ RT-DETR, การจัดการ Dataset, ระบบ RAG และ LINE Integration) ทางผู้วิจัยพบปัญหาทางเทคนิคระหว่างการดำเนินการ ซึ่งได้ทำการแก้ไขเพื่อให้ระบบทำงานได้อย่างสมบูรณ์ ดังนี้:

## 1. ปัญหาข้อจำกัดปริมาณการใช้งาน API (API Rate Limit & Quota Exceeded)
- **ลักษณะปัญหา**: ระหว่างการรันสคริปต์ประเมินผล RAGAS ด้วยคำถามทั้ง 80 ข้อ ระบบเกิดข้อผิดพลาด `ResourceExhausted: 429 Quota exceeded` จนโควตารายวันหมดและหยุดการทำงานลงกลางคัน (รันค้างอยู่ที่ประมาณ 33%)
- **สาเหตุ**: การใช้ API Key ของ Google Gemini ในรูปแบบบัญชีฟรี (Free Tier) จะถูกจำกัดโควตาการใช้งานที่เข้มงวด แม้จะมีการพยายามเปลี่ยนจากโมเดลรุ่น `Gemini 2.5 Flash` (20 ครั้ง/วัน) มาเป็นรุ่น `Gemini 3.1 Flash Lite` (500 ครั้ง/วัน) แล้ว แต่เนื่องจากกระบวนการตรวจข้อสอบของ RAGAS จะต้องยิง API วัดผลแบบ 4 มิติในทุกๆ คำถาม (รวมต้องใช้ API มากกว่า 320 ครั้ง) ทำให้โควตารายวันทะลุขีดจำกัดอย่างรวดเร็ว
- **วิธีการแก้ไข**: 
  1. **การหน่วงเวลาเพื่อหลบ Rate Limit**: ในส่วนของการตอบคำถาม (Generation) ได้เพิ่มคำสั่ง `try-except` เพื่อดักจับ Error 429 และสั่งหน่วงเวลา `time.sleep(15)` ก่อนพยายามยิงซ้ำ ซึ่งช่วยให้การสร้างคำตอบ 80 ข้อสำเร็จลุล่วงและสามารถบันทึกไว้ในไฟล์ `eval_results.json` ได้
  2. **แยกกระบวนการและสลับ LLM เป็นค่ายอื่น (Decoupled Evaluator)**: เพื่อแก้ปัญหาโควตารายวันหมด ผู้วิจัยได้ทำการแยกโค้ดส่วนกรรมการประเมินผลออกเป็นไฟล์ใหม่ (`evaluate_with_opencodezen.py`) โดยเปลี่ยนไปเรียกใช้โมเดลของค่ายอื่นที่ให้โควตาฟรีที่เสถียรกว่า เช่น **DeepSeek V4 Flash Free** (ผ่านแพลตฟอร์ม OpenCode Zen) ให้รับบทเป็นกรรมการตรวจ (Judge) แทนโมเดลของ Google ช่วยปลดล็อกข้อจำกัดด้านโควตา และทำให้โปรแกรมรันประเมินผลต่อไปจนจบได้อย่างราบรื่น

## 2. ปัญหาการเชื่อมต่อโมเดลของ RAGAS (Evaluator Model Mismatch)
- **ลักษณะปัญหา**: แม้ผู้ใช้งานจะกำหนดให้ใช้ Gemini สำหรับการตอบคำถาม แต่กระบวนการตรวจข้อสอบให้คะแนนของ RAGAS ใช้งานไม่ได้
- **สาเหตุ**: ค่าเริ่มต้นของไลบรารี RAGAS ถูกตั้งโปรแกรมมาให้เรียกใช้โมเดลของ OpenAI ในการเป็นกรรมการให้คะแนน ทำให้เกิดข้อผิดพลาดเพราะระบบไม่มี API Key ของฝั่ง OpenAI
- **วิธีการแก้ไข**: เพิ่มการตั้งค่าเชื่อมโยง `ChatGoogleGenerativeAI` เข้าไปในโมดูลของ RAGAS โดยตรง เพื่อบังคับให้ตัวประเมินผล (Evaluator) ใช้โมเดล Gemini ในการให้คะแนนแทน พร้อมกับระบุการจำกัดการประมวลผลพร้อมกัน (`max_workers=1`) เพื่อไม่ให้ยิง API เร็วเกินไป

## 3. ปัญหาความเข้ากันได้ของ Pinecone Vector Database
- **ลักษณะปัญหา**: โค้ดสร้างฐานข้อมูลแจ้งข้อผิดพลาดว่าไลบรารีไม่ถูกต้อง รวมถึงเกิดข้อผิดพลาดแจ้งเตือนขนาดมิติ (Dimension Mismatch) ระหว่างอัปโหลดข้อมูล
- **สาเหตุ**: 
  1. ไลบรารีทางการของ Pinecone มีการเปลี่ยนชื่อแพ็กเกจใหม่จาก `pinecone-client` เป็น `pinecone`
  2. โมเดล Embedding ฝั่ง Gemini (`models/gemini-embedding-001`) สร้างผลลัพธ์เวกเตอร์ที่ความยาว **3,072 มิติ** ซึ่งกว้างกว่าที่ออกแบบโครงสร้างฐานข้อมูลเริ่มต้นไว้ที่ 768 มิติ
- **วิธีการแก้ไข**: ถอนการติดตั้งไลบรารีตัวเก่าและอัปเดตไลบรารีของ Pinecone เป็นเวอร์ชันล่าสุด จากนั้นทำการลบตาราง (Index) เดิมทิ้ง และเขียนสคริปต์สร้างฐานข้อมูลใน Pinecone ใหม่ให้รองรับขนาดเวกเตอร์ที่ 3,072 มิติ

## 4. ปัญหาการแสดงผลภาษาไทยขัดข้อง (Windows Encoding Error)
- **ลักษณะปัญหา**: สคริปต์รันทำงานจนหยุดชะงักพร้อมแจ้งข้อผิดพลาด `UnicodeEncodeError: 'charmap' codec can't encode characters` 
- **สาเหตุ**: การประมวลผลผ่าน Command Prompt หรือ Terminal บนระบบปฏิบัติการ Windows มักมีปัญหาการแสดงผลและเข้ารหัสตัวอักษรภาษาไทย
- **วิธีการแก้ไข**: นำเข้าไลบรารี `sys` และ `io` เพิ่มเติม เพื่อเขียนโค้ดบังคับการเข้ารหัส (Encode) หน้าจอแสดงผล (Standard Output) ให้ใช้รูปแบบ `UTF-8` ทำให้สามารถปริ๊นท์ข้อมูลภาษาไทยออกมาระหว่างที่โปรแกรมกำลังทำงานได้ตามปกติ 
  *(อัปเดตเพิ่มเติม)* การครอบ `sys.stdout` ด้วย `TextIOWrapper` ทำให้เกิดปัญหา **Output Buffering** ทำให้การปริ๊นท์ข้อความสถานะ (เช่น Progress Bar) ไม่แสดงผลแบบ Real-time จึงต้องเพิ่มพารามิเตอร์ `line_buffering=True` เข้าไปด้วย (`sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8', line_buffering=True)`)

## 5. ปัญหาการเตรียมชุดข้อมูลภาพและการตีกรอบ (Dataset Preparation & Labeling)
- **ลักษณะปัญหา**: กระบวนการสร้างและจัดเตรียมชุดข้อมูลรูปภาพ (Image Dataset) สำหรับใช้ฝึกสอนโมเดลตรวจจับวัตถุ เป็นขั้นตอนที่กินระยะเวลาและแรงงานสูงมากที่สุด (Time-consuming) ในโครงงาน
- **สาเหตุ**: การที่จะทำให้โมเดล Object Detection (เช่น โมเดลตระกูล YOLO หรือ RT-DETR) สามารถตรวจจับและแยกแยะประเภทโรคข้าวได้อย่างแม่นยำ จำเป็นต้องใช้ภาพถ่ายใบข้าวจำนวนหลายพันภาพ และต้องอาศัยความละเอียดถี่ถ้วนในการวาดกรอบ (Bounding Box) และแปะป้ายกำกับ (Labeling) ระบุตำแหน่งของแผลโรคบนภาพทีละใบให้ถูกต้องตามหลักวิชาการ
- **วิธีการแก้ไข/แนวทางรับมือ**: 
  1. การนำชุดข้อมูลภาพถ่ายโรคข้าวแบบสาธารณะ (Public Dataset) ที่ผ่านการรับรองจากผู้เชี่ยวชาญมาใช้งานเป็นฐานเริ่มต้น เพื่อลดระยะเวลาที่ต้องลงพื้นที่ถ่ายภาพและแปะป้ายใหม่ทั้งหมด
  2. เลือกใช้เครื่องมือและแพลตฟอร์มที่ช่วยอำนวยความสะดวกในการทำ Annotation (เช่น Roboflow, LabelImg, หรือ CVAT) ซึ่งมีฟีเจอร์ช่วยตีกรอบได้รวดเร็วขึ้น และจัดสรรเวลาของแผนงานโดยเผื่อเวลาสำหรับการคลีนข้อมูลรูปภาพ (Data Cleaning) ให้มากขึ้น

## 6. ปัญหาการบันทึกผลลัพธ์จาก RAGAS Evaluation (KeyError: 0)
- **ลักษณะปัญหา**: หลังจากรันกระบวนการประเมินผลครบทุกข้อจนจบ 100% โปรแกรมกลับเกิดข้อผิดพลาด `KeyError: 0` ในขั้นตอนสุดท้ายที่กำลังจะแปลงผลลัพธ์คะแนน (EvaluationResult) ออกมาเพื่อเขียนบันทึกลงไฟล์ JSON ส่งผลให้ข้อมูลผลการประเมินที่รันมาทั้งหมด (ซึ่งใช้เวลาหลายชั่วโมง) สูญหายและไม่ได้ถูกบันทึก
- **สาเหตุ**: การอัปเดตเวอร์ชันของไลบรารี Ragas ทำให้คลาส `EvaluationResult` ไม่รองรับการแปลงเป็น Dictionary ด้วยคำสั่ง `dict(s)` แบบตรงไปตรงมาอีกต่อไป เมื่อใช้คำสั่งดังกล่าว โปรแกรมจะพยายามเข้าถึงคีย์ที่เป็นตัวเลข (Index 0) ทำให้เกิด KeyError 
- **วิธีการแก้ไข**:
  1. **เปลี่ยนวิธีการเข้าถึงข้อมูล**: แก้ไขโค้ดจากการใช้ `dict(s)` เปลี่ยนมาใช้ฟังก์ชัน `s.to_pandas()` เพื่อแปลงผลลัพธ์ให้อยู่ในรูปแบบของ Pandas DataFrame ซึ่งมีความเสถียรและสามารถจัดการข้อมูลได้ง่ายกว่า
  2. **เพิ่มระบบบันทึกผลรายข้อ (Checkpoint)**: ใช้คำสั่ง `df.to_csv('eval_details.csv')` เพื่อให้ระบบเซฟผลคะแนนแบบแยกรายข้อลงไฟล์ CSV ไว้ก่อนทันทีที่ได้ DataFrame เพื่อป้องกันกรณีโปรแกรมแครชระหว่างการคำนวณค่าเฉลี่ย
  3. **คำนวณค่าเฉลี่ยเอง**: ดึงคอลัมน์ของแต่ละ Metric จาก DataFrame มาคำนวณด้วย `df[m].mean()` แล้วจึงเก็บเป็น Dictionary ของผลรวมเฉลี่ยเพื่อบันทึกลงไฟล์ JSON ต่อไป

## 7. ปัญหาข้อจำกัดของ Provider API ในเกณฑ์ Answer Relevancy (Invalid n value)
- **ลักษณะปัญหา**: ระหว่างที่ RAGAS กำลังตรวจข้อสอบในเกณฑ์ความตรงประเด็น (Answer Relevancy) โปรแกรมเกิดข้อผิดพลาด `BadRequestError: Error from provider (DeepSeek): Invalid n value (currently only n = 1 is supported)` ทำให้ได้ค่าคะแนนกลับมาเป็น `NaN`
- **สาเหตุ**: กลไกการทำงานของเกณฑ์ `answer_relevancy` ใน RAGAS จะทำการแต่งประโยคคำถามย้อนกลับ (Reverse Engineering) จากคำตอบจำนวน 3 แบบพร้อมๆ กัน โดยส่งพารามิเตอร์ `n=3` ไปยังโมเดล LLM แต่ผู้ให้บริการ API ฝั่ง DeepSeek (ผ่าน OpenCodeZen) จำกัดให้ส่งคำขอที่ `n=1` เท่านั้น
- **วิธีการแก้ไข**: เพิ่มคำสั่งตั้งค่าการทำงานก่อนรัน RAGAS โดยบังคับให้ลดจำนวนการสุ่มคำถามย้อนกลับเหลือเพียง 1 ชุด ด้วยคำสั่ง `answer_relevancy.strictness = 1` แม้จะทำให้คะแนนอาจแกว่งขึ้นเล็กน้อย (ไม่มีตัวหารเฉลี่ย) แต่สามารถหลีกเลี่ยงข้อผิดพลาดจากฝั่ง API และประเมินผลต่อจนจบได้อย่างรวดเร็วและราบรื่น

## 8. ปัญหาเซิร์ฟเวอร์ตอบสนองไม่ทันและการติดจำกัดโควตา (TimeoutError & Rate Limit)
- **ลักษณะปัญหา**: ระหว่างการรันประเมินผลด้วย RAGAS ผ่าน API ของ OpenCodeZen (DeepSeek V4) ไปได้ระยะหนึ่ง (ประมาณ 70%) โปรแกรมแสดงข้อผิดพลาด `TimeoutError()` เรียงติดกันหลายข้อ และบางข้อขึ้น `Error 503: Service is too busy` ส่งผลให้คะแนนในข้อเหล่านั้นหายไปและกลายเป็นช่องว่าง (`NaN`)
- **สาเหตุ**: เนื่องจากเป็นการรันข้อสอบรวดเดียว 70 ข้อ (รวมการประเมิน 4 เกณฑ์ ทำให้ต้องเรียก API ถึง 280 ครั้งในเวลาไล่เลี่ยกัน) ส่งผลให้โควตา API แบบฟรีรายวันถูกใช้จนหมด (Quota Exceeded) หรือระบบของฝั่งผู้ให้บริการมองว่าเป็นการส่งคำขอที่ถี่เกินไป จึงทำการตัดการเชื่อมต่อ (Throttling) ชั่วคราว
- **วิธีการแก้ไข**:
  1. **ข้ามข้อที่ Error เพื่อรักษาผลลัพธ์ส่วนใหญ่**: ปล่อยให้โปรแกรมรันต่อไปจนจบโดยอาศัยการตั้งค่า `raise_exceptions=False` ใน RAGAS เพื่อป้องกันโปรแกรมหยุดทำงาน (Crash) ทำให้สามารถรักษาคะแนนส่วนใหญ่ที่ตรวจผ่านแล้วเซฟลงไฟล์ `eval_details.csv` ได้สำเร็จ
  2. **สร้างสคริปต์ซ่อมแซมเฉพาะจุด (Patching Script)**: สร้างสคริปต์ `03_fix_evaluate_scores.py` เพื่อโหลดไฟล์ CSV กลับมาสแกนหาเฉพาะข้อที่มีคะแนนเป็น `NaN` จากนั้นใช้ API Key อันใหม่ (ผ่านการสมัครอีเมลใหม่) มารันประเมินซ้ำ **เฉพาะข้อที่พัง** แล้วนำคะแนนมาเสียบอุดรูรั่วในตารางเดิมให้เต็ม วิธีนี้ช่วยประหยัดเวลาและโควตา API ได้ดีกว่าการต้องเริ่มรันใหม่ตั้งแต่ข้อแรกทั้งหมด (ปัจจุบันดำเนินการซ่อมแซมสำเร็จครบ 100% ทั้ง 70 ข้อแล้ว)

## 9. ปัญหาการติดตั้งไลบรารี Pinecone-Text ขัดข้องบน Windows (C++ Build Tools Error)
- **ลักษณะปัญหา**: ระหว่างการพยายามอัปเกรดระบบ RAG ให้เป็น Hybrid Search (Vector + Keyword) การติดตั้งไลบรารี `pinecone-text` เพื่อใช้คำนวณ Sparse Vector (BM25) เกิดข้อผิดพลาดร้ายแรงและไม่สามารถติดตั้งได้เนื่องจากขาด C++ Build Tools ในระบบปฏิบัติการ Windows
- **สาเหตุ**: ไลบรารี `pinecone-text` มีการเรียกใช้งานโค้ดภาษา C++ เบื้องหลังสำหรับการคำนวณอัลกอริทึม BM25 ซึ่งสภาพแวดล้อมของ Windows ทั่วไปมักไม่ได้ติดตั้ง Compiler เหล่านี้เตรียมไว้ ทำให้กระบวนการ Build ล้มเหลว
- **วิธีการแก้ไข**:
  - หลีกเลี่ยงการใช้ไลบรารี `pinecone-text` โดยตรง และเปลี่ยนมา **เขียนโค้ดคำนวณ BM25 ด้วยตนเอง (Manual Implementation)**
  - ใช้ไลบรารี `mmh3` ในการทำ Hashing คำศัพท์ และสร้างฟังก์ชันนับความถี่คำ (Term Frequency) ตามสมการ BM25 ขึ้นมาเอง
  - คำนวณค่า Document Frequency จากคลังข้อมูลทั้งหมด และบันทึกสถิติลงไฟล์ `bm25_stats.json` เพื่อใช้เป็นฐานอ้างอิงในการเข้ารหัสคำถาม (Encoding) แบบเรียลไทม์ ทำให้ได้ผลลัพธ์โครงสร้าง Sparse Vector ที่สมบูรณ์และนำเข้า Pinecone ได้โดยไม่ต้องพึ่งพาไลบรารีที่มีปัญหา

## 10. ปัญหา Context Recall ต่ำ และอาการ "ตาพร่า" ของ LLM (Information Overload)
- **ลักษณะปัญหา**: ในช่วงแรกของการปรับปรุงระบบ RAG (V3) พบว่าการเพิ่มจำนวนการดึงข้อมูล (Top-K) ไม่ช่วยให้คะแนนความครบถ้วนของเนื้อหา (Context Recall) สูงขึ้น และเมื่อเปลี่ยนมาใช้ Hybrid Search พร้อมลดขนาดก้อนข้อมูล (Chunk Size) เหลือ 1,000 (V5) คะแนนในทุกมิติกลับตกลงอย่างหนัก
- **สาเหตุ**:
  1. การหั่นข้อมูลสั้นเกินไปทำให้ **"บริบทขาดหาย"** ประโยคที่เกี่ยวข้องกันถูกจับแยกไปอยู่คนละก้อน ทำให้ LLM ขาดข้อมูลประกอบการตัดสินใจ
  2. เมื่อเพิ่มขนาดก้อนเป็น 1,500 (V4) แม้คะแนนความแม่นยำ (Faithfulness) จะพุ่งสูงสุด แต่คะแนน Recall กลับลดลง เพราะเนื้อหาที่ดึงมายาวเป็นหน้ากระดาษ ทำให้ LLM Judge ที่ทำหน้าที่ตรวจข้อสอบ (Gemini-Flash-Lite) เกิดอาการ "Lost in the middle" หรือหาประโยคสั้นๆ ที่ซ่อนอยู่ตรงกลางไม่เจอ
- **วิธีการแก้ไข**:
  - **ปรับขนาดและโครงสร้าง Chunking**: ค้นหาจุดสมดุล (Sweet Spot) โดยสรุปที่ `chunk_size=1500` และ `overlap=300` ซึ่งรักษาบริบทได้ดีที่สุด
  - **Context Enrichment**: เพิ่มการแปะชื่อโรคไว้ที่หัวกระดาษของทุกๆ Chunk เสมอ เพื่อบังคับให้ AI รู้ตัวตลอดเวลาว่ากำลังอ่านเอกสารของโรคอะไรอยู่
  - **Metadata Filtering**: เพิ่มระบบวิเคราะห์คำถาม หากผู้ใช้พิมพ์ "ชื่อโรค" ระบบจะนำคีย์เวิร์ดนั้นไปล็อคเป้า (Filter) ค้นหาเฉพาะในเอกสารของโรคนั้น ตัดข้อมูลโรคอื่นทิ้ง 100% ซึ่งวิธีนี้ช่วยแก้ปัญหา Noise ได้เด็ดขาด และทำให้คะแนนความแม่นยำ (Faithfulness) ทะลุเกณฑ์มาตรฐานพร้อมนำไปใช้งานจริง

## 11. ปัญหาการตัดคำภาษาไทย (Thai Tokenization Error) ในอัลกอริทึม BM25
- **ลักษณะปัญหา**: แม้จะหันมาเขียนระบบ Sparse Vector (BM25) ด้วยตนเอง แต่ระบบค้นหาคีย์เวิร์ดกลับทำงานได้แย่มากและแทบหาคำภาษาไทยไม่เจอ
- **สาเหตุ**: โค้ดเดิมใช้ Regular Expression (Regex) `[\w]+` ในการตัดคำ ซึ่งใช้ได้ดีกับภาษาอังกฤษที่มีการเว้นวรรค แต่เมื่อนำมาใช้กับประโยคภาษาไทยที่เขียนติดกัน Regex จะตีความสระและวรรณยุกต์ (เช่น ุ, ี, ้) เป็นจุดตัด ทำให้คำว่า *"โรคใบจุดสีน้ำตาลรักษาอย่างไร"* ถูกหั่นออกเป็นเศษขยะเช่น `['โรคใบจ', 'ดส', 'น', 'ำตาลร']` ส่งผลให้ระบบตาบอดภาษาไทยโดยสมบูรณ์
- **วิธีการแก้ไข**: นำเข้าไลบรารีปัญญาประดิษฐ์ประมวลผลภาษาไทย **`PyThaiNLP`** (`word_tokenize`) เข้ามาใช้แทน Regex ทำให้ระบบสามารถวิเคราะห์และหั่นคำไทยออกมาได้อย่างถูกต้องแบบ 100% (เช่น `['โรค', 'ใบ', 'จุด', 'สีน้ำตาล']`) ทำให้ Hybrid Search กลับมาใช้งานได้อย่างเต็มประสิทธิภาพ

## 12. ปัญหาสมการคณิตศาสตร์ BM25 ผิดเพี้ยน และคะแนนขาดสมดุล (Double Scoring & No Alpha Blending)
- **ลักษณะปัญหา**: การค้นหาแบบ Hybrid Search มีพฤติกรรมแปลกประหลาด คือให้ผลลัพธ์เหมือนการทำ Keyword Search (BM25) ธรรมดาเกือบ 100% โดยความสามารถในการตีความหมาย (Dense Vector) ของ Gemini หายไป
- **สาเหตุ**: เกิดจากบั๊กเชิงสมการและคณิตศาสตร์ 2 จุดใหญ่:
  1. **Double Scoring**: มีการนำค่าความหายากของคำ (IDF) ไปคำนวณซ้ำซ้อนทั้งฝั่งฐานข้อมูล (Document) และฝั่งคำถาม (Query) ทำให้เมื่อ Pinecone ทำการคูณเวกเตอร์ (Dot Product) ค่า IDF จะถูกจับ "ยกกำลังสอง" ทันที ทำให้คะแนนบางคำกระโดดสูงจนผิดหลักการของ BM25 ที่ถูกต้อง
  2. **No Alpha Blending**: คะแนน Dense Vector ปกติจะแกว่งอยู่ที่ `0.6 - 1.0` ในขณะที่คะแนน Sparse Vector ของ BM25 วิ่งขึ้นไปถึง `10.0 - 50.0` เมื่อไม่มีการเกลี่ยน้ำหนัก (Weighting) ก่อนรวมร่าง ทำให้คะแนน Sparse ที่มหาศาลกลบฝั่ง Dense จนมิด
- **วิธีการแก้ไข**:
  - แก้ไขสมการ BM25 โดยให้ฝั่ง Document บันทึกเฉพาะค่า `TF_norm` และฝั่ง Query คำนวณเฉพาะ `IDF * Query Freq` เพื่อให้การคูณ Dot Product ออกมาตรงตามสูตรมาตรฐานของ BM25 แบบเป๊ะๆ
  - สร้างระบบ **Alpha Blending** โดยกำหนดค่า `Alpha = 0.7` เพื่อถ่วงน้ำหนักให้ระบบพึ่งพาความฉลาดของฝั่ง Dense (Gemini) 70% และฝั่ง Sparse (BM25) 30% ทำให้สเกลคะแนนกลับมาสมดุลและทำงานร่วมกันเป็น "The Perfect Hybrid Database" ได้สำเร็จ

## 13. ปัญหา PyTorch Multiprocessing Recursion (Spawn Process Error) ในการเทรน RT-DETR บน Ubuntu
- **ลักษณะปัญหา**: เมื่อสั่งรันสคริปต์ `python train_rtdetr.py` บนระบบปฏิบัติการ Ubuntu ปรากฏข้อความตระกูล `RuntimeError: An attempt has been made to start a new process before the current process has finished...` และ `ConnectionResetError: [Errno 104]` ส่งผลให้การเทรนหยุดชะงักทันทีตั้งแต่วินาทีแรก
- **สาเหตุ**: เกิดจากการตั้งค่า `workers = 16` ใน PyTorch Dataloader บน Python 3.14/Linux ซึ่งใช้กลไกแบบ Process Spawning เมื่อโปรแกรมแตก Process ย่อยออกมาช่วยโหลดรูป Process ย่อยจะทำการอิมพอร์ตสคริปต์ `train_rtdetr.py` ซ้ำตั้งแต่บรรทัดแรก ส่งผลให้เกิดการเรียกฟังก์ชันเทรนซ้อนกันเป็นงูรวบหาง (Infinite Recursion)
- **วิธีการแก้ไข**: ห่อหุ้มโค้ดส่วนการสั่งเทรนทั้งหมดให้อยู่ภายใต้กรอบคำสั่งมาตรฐาน `if __name__ == '__main__':` พร้อมสร้างฟังก์ชัน `main()` เพื่อแยกจุดเริ่มต้นการทำงานให้ชัดเจน ป้องกันไม่ให้ Process ย่อยเรียกคำสั่งเทรนซ้ำซ้อน

## 14. ปัญหาระบบแรม (RAM Overflow) ทะลักขีดจำกัดจน OS บังคับคิลโปรแกรม (Linux OOM-Killer Crash)
- **ลักษณะปัญหา**: ในระหว่างที่โปรแกรมกำลังสแกนรูปภาพก่อนเทรน ปรากฏว่าระบบแรมของเครื่อง (64GB RAM) ถูกใช้จนเต็ม 100% ภายในไม่กี่วินาที จนส่งผลให้ระบบปฏิบัติการ Ubuntu สั่งปิดโปรแกรมอื่น (เช่น Visual Studio Code) ทิ้งเพื่อเซฟระบบ
- **สาเหตุ**: เกิดจากการเปิดตัวแปร `cache = True` ร่วมกับการตั้งค่า `workers = 16` ซึ่งการเปิด cache จะทำให้ PyTorch พยายามโหลดภาพทั้งหมด 7,416 รูปเก็บไว้ใน RAM (ประมาณ 8.5 GB) แต่เมื่อมี Process ย่อย 16 ตัว แต่ละตัวจะก๊อปปี้บล็อกแรมดังกล่าว ส่งผลให้ความต้องการแรมพุ่งสูงถึง `8.5 GB x 16 = 136 GB` ซึ่งเกินกว่า physical RAM 64GB ของเครื่อง
- **วิธีการแก้ไข**: เปลี่ยนค่านิยามเป็น `cache = False` เนื่องจากเครื่องเทรนติดตั้ง NVMe SSD 2TB ที่มีความเร็วอ่านสูงเกิน 7,000 MB/s อยู่แล้ว การอ่านจาก SSD โดยตรงร่วมกับ CPU 16 Cores ช่วยให้สามารถป้อนข้อมูลให้ GPU RTX 4090 ประมวลผลได้เต็มประสิทธิภาพ (GPU Utilization 96%) โดยไม่สูญเสียความเร็วและไม่เกิดอาการ RAM Overflow

## 15. ปัญหาโครงสร้างโฟลเดอร์ซ้อนทับ (Nested Directory Path) ในการดึงไฟล์โมเดลประเมินผล
- **ลักษณะปัญหา**: สคริปต์ประเมินผล `evaluate_model.py` หาไฟล์น้ำหนักโมเดล `best.pt` ไม่เจอ และขึ้น Error แจ้งเตือนไฟล์สูญหาย
- **สาเหตุ**: พฤติกรรมของ Ultralytics บนเครื่องเทรนมีการสร้างโฟลเดอร์ผลลัพธ์ซ้อนทับกันเนื่องจากค่า Config เดิมในระบบ เช่น `runs/detect/runs/rtdetr_rice_v1-4/` ทำให้การกำหนด Path แบบตายตัว (Hardcoded Path) เช่น `runs/rtdetr_rice_v1/` ล้มเหลว
- **วิธีการแก้ไข**: ปรับปรุงฟังก์ชัน `get_latest_run_folder()` ใน `evaluate_model.py` ให้อ่านไฟล์แบบค้นหาแนวลึก (Recursive Search `**/{prefix}*/weights/best.pt`) เพื่อทำการสแกนหาไฟล์ `best.pt` ทุกซอกทุกมุมของโฟลเดอร์ และทำการจัดลำดับตามเวลาอัปเดตล่าสุด ทำให้ระบบสแกนเจอโมเดลรอบใหม่ล่าสุดอย่างถูกต้อง 100% ไม่ว่าจะถูกสร้างไว้ในโครงสร้างโฟลเดอร์แบบใด

## 16. ปัญหา Relative Dataset Path Resolution บน Linux (FileNotFoundError: dataset.yaml)
- **ลักษณะปัญหา**: เมื่อสั่งรันสคริปต์ `python3 training/train_rtdetr_v2.py` จากโฟลเดอร์หลักของโปรเจกต์ ระบบ Ultralytics แจ้งเตือนข้อผิดพลาด `FileNotFoundError: Dataset .../training/data/labeled/valid/images not found` และหยุดการทำงานลงทันที
- **สาเหตุ**: ในไฟล์ `training/dataset.yaml` มีการกำหนดเส้นทางแบบถอยหลังหนึ่งชั้น (`path: ../data/labeled`) เมื่อสั่งรันสคริปต์จากภายนอกโฟลเดอร์ `training/` ตัว Dataloader ของ Ultralytics จะนำ Path ไปคำนวณซ้อนกับตำแหน่งปัจจุบัน ทำให้เส้นทางเพี้ยนและหาโฟลเดอร์ภาพไม่พบ
- **วิธีการแก้ไข**: เพิ่มคำสั่งกำหนดตำแหน่งการทำงานล่วงหน้า `current_dir = os.path.dirname(os.path.abspath(__file__))` และสั่ง `os.chdir(current_dir)` ที่บรรทัดแรกของฟังก์ชัน `main()` ในทั้ง `train_rtdetr_v2.py` และ `evaluate_model.py` เพื่อบังคับให้ Working Directory ย้ายเข้าสู่โฟลเดอร์ `training/` เสมอ ทำให้การอ้างอิง Relative Path ของ Dataset ถูกต้อง 100% ไม่ว่าจะสั่งรันจากไดเรกทอรีใด

## 17. ปัญหา JSON Formatting ขัดข้องเมื่อส่งข้อความหลายบรรทัดจาก n8n สู่ LINE Bot API (Bad Control Character)
- **ลักษณะปัญหา**: เมื่อ n8n ได้รับผลการวินิจฉัยโรคและคำแนะนำวิชาการจาก RAG แล้วพยายามส่งข้อความภาษาไทยที่มีการขึ้นบรรทัดใหม่ (`\n`) กลับไปยัง LINE API โหนด HTTP Request เกิดข้อผิดพลาด `Bad control character in string literal` ส่งผลให้แชทบอทไม่ส่งข้อความตอบกลับผู้ใช้
- **สาเหตุ**: การนำตัวแปรที่มีอักขระขึ้นบรรทัดใหม่ (`\n`) หรือเครื่องหมายคำพูด (Quotes) ไปแปะลงในช่อง JSON Body ของ n8n ตรงๆ ทำให้โครงสร้าง JSON เสียหาย (Invalid JSON Syntax)
- **วิธีการแก้ไข**: ปรับปรุง Expression ในโหนด HTTP Request ของ n8n โดยใช้ฟังก์ชัน `JSON.stringify({...})` ครอบ Payload ทั้งหมด เพื่อทำการแปลงและ Escape อักขระพิเศษ (`\n`, `\"`) ให้เป็นไปตามมาตรฐาน JSON สากลอย่างถูกต้อง

## 18. ปัญหาการสื่อสารข้ามเครือข่ายระหว่าง n8n Docker Container กับ FastAPI บน Host OS (Connection Refused)
- **ลักษณะปัญหา**: n8n ที่รันอยู่ภายใน Docker Container ไม่สามารถส่งคำขอ HTTP ไปยัง FastAPI Service (`http://localhost:8000`) ที่รันอยู่บน Host Machine ได้ ทำให้เกิดข้อผิดพลาด Connection Refused
- **สาเหตุ**: ภายในระบบคอนเทนเนอร์ คำว่า `localhost` จะหมายถึงตัว Docker Container เอง ไม่ใช่เครื่องเซิร์ฟเวอร์หลัก (Host)
- **วิธีการแก้ไข**: เพิ่มการตั้งค่า `extra_hosts: ["host.docker.internal:host-gateway"]` ในไฟล์ `n8n/docker-compose.yml` และเปลี่ยน URL Endpoint ใน n8n Workflow จาก `localhost:8000` เป็น `http://host.docker.internal:8000` ทำให้ Container สื่อสารกับบริการบน Host ได้อย่างราบรื่น

## 19. ปัญหาการส่ง Header ยืนยันตัวตนดึงรูปภาพจาก LINE API ใน n8n (401 Unauthorized)
- **ลักษณะปัญหา**: โหนด Fetch Image from LINE API ใน n8n ไม่สามารถดาวน์โหลดรูปภาพใบข้าวที่ผู้ใช้ส่งมาได้ โดย LINE API ตอบกลับด้วยรหัส 401 Unauthorized แม้จะระบุ Channel Access Token ในส่วน Header เรียบร้อยแล้ว
- **สาเหตุ**: ในไลบรารีโหนด HTTP Request เวอร์ชัน 3 ของ n8n หากไม่ได้เปิดใช้งานพารามิเตอร์ `"sendHeaders": true` ตัวโหนดจะไม่ส่ง Header ที่กำหนดไว้ไปยังเซิร์ฟเวอร์ปลายทาง
- **วิธีการแก้ไข**: เพิ่มค่าคอนฟิก `"sendHeaders": true` และ `"specifyHeaders": "keypair"` ในโครงสร้าง Workflow JSON ของ n8n ส่งผลให้ระบบแนบ Authorization Token ได้อย่างถูกต้องและสามารถดึงไฟล์ภาพ Binary จาก LINE สำเร็จ

## 20. ปัญหาผลกระทบทางสัณฐานวิทยาของรอยโรคจาก Mosaic Augmentation (Morphological Distortion on Elongated Lesions)
- **ลักษณะปัญหา**: ในการเทรนปรับปรุงโมเดล RT-DETR-L v2 พบว่าโรคที่มีรอยโรคกว้างและชัดเจนอย่าง Leaf Blast (+4.2%) และ Sheath Blight (+1.3%) มีค่าความแม่นยำและ Precision เพิ่มขึ้นสูงมาก แต่โรคที่มีแผลขนานยาวแคบอย่าง Bacterial Leaf Blight (BLB) และ Leaf Scald กลับมีคะแนนลดลง
- **สาเหตุ**: กระบวนการ Mosaic Augmentation (การนำ 4 ภาพมารวมเป็น 1 ภาพ) ทำให้รอยโรคที่เป็นริ้วยาวแคบตามแนวขอบใบ (High Aspect Ratio) ถูกบีบอัดขนาดลงเหลือเพียง 1-3 พิกเซล ส่งผลให้ Transformer Attention Layer มองเห็นเป็นสัญญาณรบกวน (Noise) ประกอบกับโมเดลมีค่า Precision สูงขึ้นจึงระมัดระวังตัว ไม่ยอมตีกรอบในจุดที่กำกวม
- **วิธีการแก้ไข/ข้อเสนอแนะเชิงวิชาการ**: บันทึกข้อค้นพบเป็นประเด็นอภิปรายในบทที่ 4-5 ของเล่มปริญญานิพนธ์ โดยชี้ให้เห็นว่าการปรับปรุงเฉพาะ Hyperparameters แบบครอบจักรวาลมีข้อจำกัดต่อรอยโรคที่มีลักษณะกายภาพพิเศษ และเสนอแนะให้ใช้แนวทาง Data-Centric AI (Re-labeling Bounding Box) ร่วมกับการทำ Class-Specific Augmentation ในงานวิจัยขั้นต่อไป

## 21. ปัญหา Linux OOM-Killer บังคับปิดโปรแกรมทันทีจากการใช้ RAM Caching ที่ภาพความละเอียดสูง (Linux OOM-Killer Crash on High-Resolution `cache='ram'`)
- **ลักษณะปัญหา**: เมื่อสั่งรันสคริปต์ `train_rtdetr_v4.py` ที่ขนาดภาพ `imgsz=800` โดยเปิดตัวแปร `cache='ram'` โปรแกรมหยุดทำงานและเด้งกลับมาที่หน้า Terminal ทันทีหลังจากกด Enter โดยไม่มีข้อความ Error หรือ Traceback ฟ้องแม้แต่บรรทัดเดียว
- **สาเหตุ**: การแคชภาพขนาด 800x800 จำนวน 7,416 รูปเก็บไว้ใน RAM เมื่อ PyTorch Dataloader แตก Worker Threads ออกมา 8 ตัว จะเกิดปรากฏการณ์ RAM Allocation Spike ทะลุเกินขีดจำกัด 64GB ของเครื่องในเสี้ยววินาที ส่งผลให้เคอร์เนลของ Linux ส่งสัญญาณ `SIGKILL` (Exit code 137) สั่งประหารโพรเซส Python ทันทีเพื่อป้องกันระบบปฏิบัติการค้าง
- **วิธีการแก้ไข**: เปลี่ยนจากการแคชลง RAM มาใช้ฟังก์ชัน **`cache = 'disk'`** เพื่อให้ระบบแปลงและแคชภาพเป็นไฟล์ไบนารี (`.npy`) เก็บไว้บน NVMe SSD 2TB ความเร็วสูงแทน ซึ่งช่วยให้โหลดภาพได้เร็วขึ้น 15% – 30% โดยที่ RAM ใช้งานเพียง 6–8 GB ปลอดภัยจากปัญหา Linux OOM-Killer 100%

## 22. ปัญหาข้อความแจ้งเตือน Grid Sampler 2D บน CUDA และการรันแบบ Deterministic (CUDA Grid Sampler Non-deterministic Warning)
- **ลักษณะปัญหา**: ในระหว่างการเทรน RT-DETR ปรากฏข้อความเตือนสีแดง `UserWarning: grid_sampler_2d_backward_cuda does not have a deterministic implementation...` พ่นออกมาขัดจังหวะหน้าจอ Terminal ทุก Epoch
- **สาเหตุ**: สถาปัตยกรรม Transformer ของ RT-DETR มีการใช้ฟังก์ชัน `grid_sampler_2d` สำหรับสุ่มพิกัด Feature Grid ซึ่งบนฮาร์ดแวร์ CUDA จะทำงานแบบคู่ขนาน (Parallel Atomic Operations) ที่ไม่สามารถการันตีการรันซ้ำแบบ Deterministic ได้ 100%
- **วิธีการแก้ไข**: เพิ่มคำสั่ง `warnings.filterwarnings("ignore", category=UserWarning)` และ `warnings.filterwarnings("ignore", message=".*grid_sampler_2d_backward_cuda.*")` ที่ส่วนต้นของสคริปต์ พร้อมตั้งค่า `deterministic=False` ใน `model.train()` เพื่อปิดข้อความเตือนที่ไม่จำเป็น และปล่อยให้การ์ดจอ CUDA ประมวลผลแบบคู่ขนานด้วยความเร็วสูงสุด

## 23. ปัญหาความซับซ้อนของการคำนวณแบบยกกำลังสองใน Vision Transformer เมื่อเพิ่มขนาดภาพ (Quadratic Computational Complexity in Transformer Attention at High Resolution)
- **ลักษณะปัญหา**: เมื่อเพิ่มขนาดภาพอินพุตจาก `640x640` เป็น `800x800` ในโมเดล RT-DETR-L พบว่าความเร็วในการเทรนลดลงเกือบเท่าตัว (จาก 4.5 it/s เหลือ 2.4 it/s และเวลาต่อรอบเพิ่มจาก 1:40 นาที เป็นเกือบ 3 นาที)
- **สาเหตุ**: สถาปัตยกรรม Vision Transformer (AIFI และ Cross-Attention Decoder) มีภาระการคำนวณแบบ Quadratic Complexity ($O(N^2)$) เมื่อจำนวน Token เพิ่มขึ้นจาก 400 จุด (ที่ 640px) เป็น 625 จุด (ที่ 800px) ภาระการคำนวณ Attention Matrix จะเพิ่มขึ้นถึง 2.44 เท่า (จาก 160,000 ครั้ง เป็น 390,625 ครั้ง) ส่งผลให้ GFLOPs พุ่งจาก ~105 GFLOPs เป็น ~170 GFLOPs
- **วิธีการแก้ไข/ข้อสรุปเชิงวิชาการ**: เปิดใช้งาน `cache='disk'` ร่วมกับ `workers=16` และ `torch.backends.cudnn.benchmark = True` เพื่อเร่งความเร็วการป้อนข้อมูลระดับฮาร์ดแวร์ให้ทันกับความต้องการของ GPU พร้อมบันทึกข้อค้นพบเชิงวิชาการเรื่อง Trade-off ระหว่าง Resolution และ Training Latency ในเล่มวิจัยบทที่ 4-5
